# 详细设计 04 —— 首次接入初始化引导（客户自助填报）

> 版本：v1.0
> 日期：2026-10-27
> 状态：可进入开发
> 说明：解决"新客户接入时，服务方如何高效采集客户资料"的问题。通过小程序引导客户自助填报，替代人工逐项收集。

---

## 一、模块定位（第一性原理）

新客户接入交付服务时，服务方需要采集三类资料才能开展服务：

1. **企业基础资料** —— 企业是谁、资质如何
2. **人档 + 车档资料** —— 有哪些人、哪些车
3. **安全管理现状** —— 客户当前安全底子（用于诊断和制定服务方案）

传统方式是人工线下收集（发表格、催资料、对账），效率低、易漏。本模块把采集过程**产品化**：客户在小程序上自助分步填报，数据直接落库，服务方（超管/运营方）在 PC 端实时查看。

> 核心价值：**把"服务方催资料"变成"客户自助填 + 系统自动收集"**。

---

## 二、产品决策记录（已确认）

| 决策项 | 结论 |
|--------|------|
| 填报人 | **企业负责人/管理员**（司机角色不参与接入流程） |
| 填报形式 | **引导式分步流程**（进度条，未填完不能正常使用系统） |
| 安全现状 | **选择 + 开放结合**（选择题打底，文本框补细节） |
| 采集端 | **小程序**填报 + **PC 端**（服务方）查看汇总 |
| 字段来源 | **严格对齐原系统**，原系统有什么字段就用什么字段，不自行删减 |
| 接入采集范围 | **只采集原系统标 `*必填` 的核心字段**，选填项后续 PC 端补 |

## 三、填报流程设计

### 3.1 三步引导流程

```
第一步：企业基础资料
   ↓
第二步：人档 + 车档资料
   ↓
第三步：安全管理现状
   ↓
提交 → 完成接入
```

进度条（小程序顶部）：`①企业资料 → ②人车档案 → ③安全现状`，逐步解锁，填完当前步才能进下一步。

### 3.2 分步明细

#### 第一步：企业基础资料

复用「企业信息管理」模块的字段，但精简为**接入必填项**（其他可后续补）：

| 字段 | 必填 | 说明 |
|------|------|------|
| 企业名称 | ✅ | |
| 统一社会信用代码 | ✅ | |
| 营运类型 | ✅ | 货运/客运/危货 |
| 经营期限 | ✅ | 长期/日期 |
| 所在地 | ✅ | |
| 安全主要负责人 | ✅ | |
| 负责人电话 | ✅ | |
| 从业人员数量 | | |
| 车辆规模 | | |
| 营业执照图片 | ✅ | 拍照/相册上传 |
| 经营许可证图片 | | |

#### 第二步：人档 + 车档资料

**人档（批量/逐个录入）**：

> 字段严格对齐原系统「人员基础信息 / 一人一档」模块。接入阶段**只采集影响系统功能的必填项**，其余不影响功能的字段后续补充。

| 字段 | 必填 | 说明 |
|------|------|------|
| 姓名 | ✅ | 缺了无法建立人员档案 |
| 手机号 | ✅ | 缺了无法关联账号/提醒 |
| 岗位 | ✅ | 缺了无法分配权限（驾驶员/安全员等） |
| 性别 | 非必填 | 不影响功能，后续补 |
| 政治面貌 | 非必填 | 不影响功能，后续补 |
| 部门 | 非必填 | 不影响功能，后续补 |
| 证照（驾驶证/从业资格证等） | 非必填 | 不影响功能，后续补 |

> **必填标准**：是否影响系统功能运转。姓名/手机号/岗位缺了系统跑不动，故必填；其余后续补。

**车档（批量/逐个录入）**：

> 字段严格对齐原系统「车辆基础信息 / 一车一档」模块。接入阶段**只采集影响系统功能的必填项**。

| 字段 | 必填 | 说明 |
|------|------|------|
| 车牌号 | ✅ | 车辆唯一标识，缺了无法建档 |
| 营运类型 | ✅ | 影响三检/预警等业务逻辑 |
| 车牌颜色 | ✅ | 影响车辆识别 |
| 运输类型 | ✅ | 影响业务逻辑 |
| 车辆识别代码 VIN 号 | 非必填 | 不影响功能，后续补 |
| 所属企业 | 非必填 | 单企业场景下默认为本企业 |
| 车辆类型 | 非必填 | 不影响功能，后续补 |
| 行驶证图片 | 非必填 | 不影响功能，后续补 |

> 提供「批量录入」：粘贴表格 / 逐个添加两种方式，降低几十辆车的录入成本。

#### 第三步：安全管理现状（选择 + 开放结合）

**结构化选择题**（快速判断客户底子，服务方一眼定位）：

| 维度 | 问题 | 选项 |
|------|------|------|
| 制度 | 是否已有安全生产制度？ | 有 / 部分有 / 没有 |
| 人员 | 是否有专职安全管理人员？ | 有 / 无 / 兼职 |
| 台账 | 是否有安全台账（三检/会议/培训记录）？ | 有电子台账 / 有纸质 / 没有 |
| 三检 | 车辆是否执行一日三检？ | 严格执行 / 偶尔 / 不执行 |
| 培训 | 是否定期开展安全培训？ | 是 / 否 |
| 隐患 | 是否做过隐患排查？ | 定期做 / 偶尔 / 没做过 |

**开放补充**（文本框，客户自由描述）：

> "请简要说明贵企业当前安全管理情况、希望我们重点帮您解决的问题"（可空）

## 四、数据模型

```sql
-- 接入初始化状态（跟踪企业接入进度）
CREATE TABLE onboarding (
  id            BIGINT PRIMARY KEY,
  tenant_id     BIGINT NOT NULL,
  step          TINYINT DEFAULT 1,          -- 当前进行到第几步（1/2/3）
  status        TINYINT DEFAULT 0,          -- 0进行中 1已完成
  completed_at  DATETIME,
  created_at    DATETIME DEFAULT NOW()
);

-- 安全管理现状（选择题答案，可扩展）
CREATE TABLE onboarding_status (
  id           BIGINT PRIMARY KEY,
  tenant_id    BIGINT NOT NULL,
  dimension    VARCHAR(50) NOT NULL,        -- 维度：system/staff/ledger/check/train/danger
  answer       VARCHAR(50),                 -- 选择答案
  remark       VARCHAR(500),                -- 开放补充（全局一个即可）
  updated_at   DATETIME
);
```

> 说明：
> - 企业基础资料 → 复用 `tenant_info` / `tenant_cert` 表
> - 人档 → 复用 `person` 表（后续模块）
> - 车档 → 复用 `vehicle` 表（后续模块）
> - 现状 → 独立 `onboarding_status` 表

## 五、页面交互设计

### 5.1 小程序端（客户填报）

**入口**：企业负责人/管理员登录小程序后，若企业处于「待接入」状态，首页显示「完成企业资料登记」卡片，点击进入分步流程。

```
┌─────────────────────────┐
│  完成企业资料登记        │  ← 醒目引导
│  ① 企业资料 → ② 人车档案 → ③ 安全现状  │
└─────────────────────────┘
```

**分步页面**：
- 顶部进度条 + 步骤标题
- 表单字段（适老化：大字、大按钮、点选为主）
- 图片上传：拍照/相册
- 底部「保存并下一步」大按钮
- 最后一步「提交」按钮

### 5.2 PC 端（服务方/超管查看）

**企业接入列表**：展示各企业接入状态（进行中/已完成）、当前到第几步、填报完整度。

**企业接入详情**：查看该企业填写的三块资料（基础资料、人车列表、安全现状），用于服务方诊断和制定方案。

## 六、状态流转

```
待接入 ──企业负责人登录──> 进行中(第1步→第2步→第3步) ──提交──> 已完成
```

| 状态 | 说明 |
|------|------|
| 待接入 | 企业已开通但未开始填报 |
| 进行中 | 正在分步填报（记录当前 step） |
| 已完成 | 三块资料填完提交 |

**约束**：企业处于「待接入/进行中」时，小程序端只显示接入引导，其他业务功能暂不可用（完成接入后解锁）。

## 七、接口定义

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/api/onboarding/status` | 获取当前企业接入状态（进行到哪步） |
| POST | `/api/onboarding/step1` | 提交企业基础资料 |
| POST | `/api/onboarding/step2/person` | 提交人员（批量） |
| POST | `/api/onboarding/step2/vehicle` | 提交车辆（批量） |
| POST | `/api/onboarding/step3` | 提交安全管理现状 |
| POST | `/api/onboarding/submit` | 完成接入 |
| GET | `/api/onboarding/list` | 服务方查看企业接入列表（超管） |
| GET | `/api/onboarding/{tenantId}` | 查看某企业接入详情（超管） |

## 九、与其他模块的关系

| 模块 | 关系 |
|------|------|
| 企业信息管理（03） | 第一步填报的数据直接写入 `tenant_info`，字段对齐该模块 |
| 人员档案（待设计） | 第二步人档写入 `person` 主表，字段对齐原系统「人员基础信息」 |
| 车辆档案（待设计） | 第二步车档写入 `vehicle` 主表，字段对齐原系统「车辆基础信息」 |
| 组织权限（01） | 企业「待接入」状态通过 `sys_tenant.status` 或 onboarding 状态控制 |

> **重要设计原则**：接入流程不单独定义字段，而是**复用各业务模块的正式字段**。接入阶段只要求填写原系统标 `*必填` 的字段，其余选填项后续在 PC 端对应模块补齐。这样避免"接入字段"与"正式字段"两套数据不一致。

## 九、原型接入引导页（onboarding_guide.html）

> 高保真原型中提供独立的「**新企业接入引导**」页面（`pc/onboarding_guide.html`），挂在「服务商运营」菜单下，作为服务商交付新企业的**总导航**。

- **六阶段进度条**：签约开户 → 资料采集 → 静态资料全面整改 → 小程序账号开通 → 台账归档 → 日常运营（与《产品需求确认文档》第十一章「企业签约后的完整交付与运营流程」阶段 0–5 一一对应）。
- **每阶段可跳转**：页面列出该阶段要做的操作（如「资料采集」指向智能收集 / 人车档案录入、「静态资料全面整改」指向范本管理 / 制度预案生成、「小程序账号开通」指向人员管理、「台账归档」指向电子档案柜），按钮 `gotoPage()` 跳转到对应模块，形成「引导页 → 实际功能」的闭环。
- **受众**：服务商运营人员（交付新客户时使用）；企业侧无需进入此页，由小程序接入引导承接（见上方三 / 四节）。

## 十、开发任务拆解

1. 建表（onboarding / onboarding_status）
2. 三步填报接口
3. 小程序分步填报页面（进度条 + 表单 + 上传）
4. 接入状态判断 + 首页引导卡片
5. 未完成接入时锁定业务功能的逻辑
6. PC 端接入列表 + 详情页

---

## 十一、验收标准

1. 企业负责人登录小程序，能看到「完成企业资料登记」引导
2. 三步分步填报，进度条正确，填完才能进下一步
3. 图片能拍照/相册上传
4. 提交后，服务方 PC 端能实时看到该企业三块资料
5. 未完成接入前，小程序其他业务功能锁定；完成后解锁
