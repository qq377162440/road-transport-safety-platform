# 详细设计 02 —— 审批引擎 + 预警引擎（通用基础设施）

> 版本：v1.0
> 日期：2026-10-27
> 状态：可进入开发
> 说明：这是两个**通用能力**，被多个业务模块复用。先于业务模块设计，后续制度评审、安全投入、事故上报等直接引用本设计。

---

## 第一部分：审批引擎

### 一、定位（大白话）

很多业务都需要"走流程签字"：

- 制度评审修订：安全科负责人 → 分管安全副总 → 总经理（三级）
- 安全投入预算：发起 → 审核
- 事故上报：上报 → 审批

与其每个模块各写一套"提交→审批→通过/驳回"，不如做一个**通用的审批工具**，各模块都调它。

### 二、设计原则（已拍板：简单串行审批）

| 原则 | 说明 |
|------|------|
| **串行** | 一级一级往上走，前一级通过才到下一级 |
| **固定步数** | 每个业务场景审批几级、每级谁审，是预先配好的 |
| **不搞会签/并行/条件分支** | 保持简单，普通安全员也能看懂 |

### 三、核心概念

```
审批流程(Process) —— 业务发起时创建，绑定一条业务数据
  ├─ 节点1(Node)：审批人A → 通过/驳回
  ├─ 节点2(Node)：审批人B → 通过/驳回
  └─ 节点3(Node)：审批人C → 通过/驳回 → 流程完成
```

- **流程 Process**：一次审批的实例，如"《安全责任制》2026修订申请"
- **节点 Node**：流程中的一级，如"安全科负责人审批"
- **业务类型 biz_type**：标识这个审批是哪个模块的（制度评审 / 安全投入 / 事故上报）

### 四、状态流转

```
待提交 ──提交──> 审批中 ──全部通过──> 已通过
                    │
                    ├─ 某级驳回 ──> 已驳回（可重新提交，回到审批中）
                    │
                    └─ 发起人撤回 ──> 已撤回
```

**关键规则**：
- 驳回后，发起人修改内容可**重新提交**，流程从头或从驳回节点重新开始（默认从头）
- 通过/驳回都要填**审批意见**（留痕，免责取证需要）

### 五、数据模型

```sql
-- 审批流程实例
CREATE TABLE flow_process (
  id            BIGINT PRIMARY KEY,
  tenant_id     BIGINT NOT NULL,
  biz_type      VARCHAR(30) NOT NULL,      -- 业务类型：doc_review / budget / accident
  biz_id        BIGINT NOT NULL,           -- 关联业务数据ID
  title         VARCHAR(200),              -- 标题，如"《安全责任制》2026修订"
  status        TINYINT DEFAULT 1,         -- 1待提交 2审批中 3已通过 4已驳回 5已撤回
  current_node  INT DEFAULT 1,             -- 当前审批到第几级
  total_node    INT NOT NULL,              -- 总共几级
  submitter_id  BIGINT,                    -- 发起人
  created_at    DATETIME DEFAULT NOW()
);

-- 审批节点（每一级）
CREATE TABLE flow_node (
  id           BIGINT PRIMARY KEY,
  process_id   BIGINT NOT NULL,
  node_order   INT NOT NULL,               -- 第几级（1,2,3...）
  node_name    VARCHAR(50),                -- 节点名，如"安全科负责人审批"
  approver_id  BIGINT,                     -- 审批人（用户ID）
  status       TINYINT DEFAULT 0,          -- 0待审 1通过 2驳回
  comment      VARCHAR(500),               -- 审批意见
  approved_at  DATETIME
);

-- 审批配置（定义每种业务类型的审批模板）
CREATE TABLE flow_config (
  id           BIGINT PRIMARY KEY,
  tenant_id    BIGINT NOT NULL,
  biz_type     VARCHAR(30) NOT NULL,       -- 业务类型
  biz_name     VARCHAR(50),                -- 显示名
  node_order   INT NOT NULL,               -- 第几级
  node_name    VARCHAR(50),                -- 节点名
  role_id      BIGINT,                     -- 该级由哪个角色审批（如"安全科负责人"角色）
  UNIQUE KEY (tenant_id, biz_type, node_order)
);
```

### 六、接口定义

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | `/api/flow/start` | 发起审批（业务模块提交时调用） |
| GET | `/api/flow/{id}` | 查看审批详情（含各级节点状态） |
| POST | `/api/flow/{id}/approve` | 审批（通过/驳回 + 意见） |
| POST | `/api/flow/{id}/withdraw` | 发起人撤回 |
| GET | `/api/flow/todo` | 我的待办（待我审批的） |
| GET | `/api/flow/done` | 我的已办 |
| GET | `/api/flow/mine` | 我发起的 |

### 七、页面交互

**通用审批组件**（嵌入各业务模块）：
- 发起：业务表单底部「提交审批」按钮 → 创建流程
- 待办列表：PC 首页/消息中心展示"待我审批"，点击进入业务详情 + 审批面板
- 审批面板：显示流程进度条（第1级→第2级→第3级，标绿/灰），通过/驳回按钮 + 意见输入框

**流程进度条示意**：
```
[安全科负责人] → [分管安全副总] → [总经理]
   ✓ 已通过        ● 审批中          ○ 待审批
```

## 第二部分：预警引擎

### 八、定位（大白话）

平台里有很多"过期就违规"的东西：

- 驾驶证、从业资格证、行驶证、营运证到期
- 车辆保险到期
- 劳动合同到期
- 培训没完成
- 三检没做
- 隐患超期没整改

如果让用户自己挨个去查，一定会漏。所以做一个**统一的预警引擎**：定时扫描这些数据，发现快到期/已逾期，就生成预警，**主动推到首页和消息中心**提醒。

### 九、核心概念

| 概念 | 说明 |
|------|------|
| 预警规则 Warn Rule | 定义"什么条件触发预警"，如"证照剩余天数 ≤ 30 天" |
| 预警记录 Warn Record | 一条具体的预警，如"张三的从业资格证 30 天后到期" |
| 预警等级 | 严重（已逾期/即将逾期）· 一般（临近）· 提示（提醒） |

### 十、预警类型清单

| 预警类型 | 数据来源表 | 触发条件 | 等级 |
|---------|-----------|---------|------|
| 人员证照到期 | person_cert | 剩余 ≤ 30 天 | 一般 |
| 人员证照逾期 | person_cert | 已过期 | 严重 |
| 车辆证照到期 | vehicle_cert | 剩余 ≤ 30 天 | 一般 |
| 车辆保险到期 | vehicle_insurance | 剩余 ≤ 30 天 | 一般 |
| 劳动合同到期 | person_contract | 剩余 ≤ 30 天 | 提示 |
| 培训未完成 | 培训模块 | 超期未完成 | 一般 |
| 三检未完成 | check 模块 | 当日未完成 | 提示 |
| 隐患逾期 | danger 模块 | 超期未闭环 | 严重 |

### 十一、预警等级与颜色（沿用设计系统）

| 等级 | 颜色 | 含义 |
|------|------|------|
| 严重 | 红 `#d92b2b` | 已逾期 / 已过期，需立即处理 |
| 一般 | 橙 `#e88600` | 临近到期，需尽快处理 |
| 提示 | 蓝 `#1a5cb0` | 提醒类，按需处理 |

### 十二、数据模型

```sql
-- 预警规则（可配置）
CREATE TABLE warn_rule (
  id           BIGINT PRIMARY KEY,
  tenant_id    BIGINT NOT NULL,
  warn_type    VARCHAR(30) NOT NULL,       -- 预警类型
  days_before  INT DEFAULT 30,             -- 提前多少天预警
  level        TINYINT DEFAULT 2,          -- 1严重 2一般 3提示
  enabled      TINYINT DEFAULT 1
);

-- 预警记录
CREATE TABLE warn_record (
  id           BIGINT PRIMARY KEY,
  tenant_id    BIGINT NOT NULL,
  warn_type    VARCHAR(30) NOT NULL,
  level        TINYINT NOT NULL,           -- 1严重 2一般 3提示
  title        VARCHAR(200),               -- 如"张三 从业资格证 30天后到期"
  target_type  VARCHAR(30),                -- person_cert / vehicle_insurance...
  target_id    BIGINT,                     -- 关联数据ID
  status       TINYINT DEFAULT 0,          -- 0未处理 1已处理 2已忽略
  expire_date  DATETIME,                   -- 到期时间
  created_at   DATETIME DEFAULT NOW()
);
```

### 十三、工作流程

```
定时任务（每小时）扫描各业务表
  → 按 warn_rule 判断是否触发
  → 生成 warn_record
  → 推送：PC 首页"待办"卡片 + 小程序首页 + 消息中心
  → 用户处理（如更新证照）后，预警记录标记"已处理"
```

### 十四、页面交互

- **PC 首页**：顶部"接下来该做这 3 件事"卡片，其中一步就是"补传 5 个到期证件"（由预警引擎驱动）
- **小程序首页**：司机视角/管理视角都有预警入口
- **预警中心**（PC 独立页）：所有预警记录列表，按等级筛选，点击跳转到对应业务处理

---

## 十五、两个引擎的关系

| | 审批引擎 | 预警引擎 |
|--|---------|---------|
| 触发方式 | 人为发起（提交审批） | 系统自动（定时扫描） |
| 驱动方向 | 业务 → 引擎（业务调审批） | 引擎 → 业务（预警推给业务） |
| 复用场景 | 制度评审、安全投入、事故上报 | 证照/保险/合同/培训/三检/隐患 |

---

## 十六、开发任务拆解

**审批引擎**：
1. 建表（flow_process / flow_node / flow_config）
2. 审批配置 CRUD（配置各业务类型几级、每级什么角色）
3. 发起/审批/撤回/查询接口
4. 待办/已办/我发起列表
5. 通用审批组件（进度条 + 审批面板）

**预警引擎**：
1. 建表（warn_rule / warn_record）
2. 预警规则配置
3. 定时扫描任务（各业务表到期扫描）
4. 预警记录生成 + 推送
5. 预警中心页面 + 两端首页集成

---

## 十七、验收标准

**审批引擎**：
1. 制度评审能走通"三级串行审批"，前一级通过才到下一级
2. 驳回后发起人可修改重新提交
3. 每级审批意见留痕
4. 待办列表正确展示"待我审批"

**预警引擎**：
1. 证照剩余 30 天内自动生成预警，推到首页
2. 已过期证照标记为"严重"（红色）
3. 处理证照后预警自动标记"已处理"
4. 预警规则可配置（提前天数、等级）
