## 二、总体架构决策

### 2.1 架构风格

| 决策项 | 结论 |
|--------|------|
| 架构风格 | **单体模块化**（一个后端，按业务模块分包，非微服务） |
| 理由 | 初期复杂度低、易扩展；未来按需拆微服务 |

**关键取舍**：原系统是「5 个独立子系统 + passport 认证中心」的微服务架构，我们**不复刻**这套，改为单体模块化 + JWT 内聚认证。未来若拆微服务，只需把 `/auth` 模块独立，其余无感。

### 2.2 端范围

| 端 | 定位 | 用户 |
|----|------|------|
| **PC 网页端** | 管理 + 台账 + 数据 | 企业管理员、安全员、法人、运营方超管 |
| **微信小程序端** | 执行 + 填报 + 查看 | 驾驶员、押运员、管理人员（管理视角） |

> **不做独立运营后台**。运营管理并入 PC 端，通过「平台级超级管理员 / 服务商账号」账号实现（见 4.5；服务商账号的核心职责是管理系统模板/视频库/题库等配置，见 01 文档 3.2）。

## 四、关键架构决策（本轮新增拍板）

### 4.0 字段设计总原则（重要）

> **所有业务模块的字段，严格对齐原系统**。原系统（cloud.ygg360.cn）就是最权威的字段来源，逆向报告已核实 50 个模块的完整字段。**禁止自行删减、简化、臆造字段**——原系统有什么字段，我们就有什么字段。

**必填项的判定标准**：不是照搬原系统的 `*` 标记，而是看**该字段是否影响系统功能**。

| 类型 | 判定标准 | 示例 |
|------|---------|------|
| 必填 | 缺了系统功能无法运转 | 人档的「姓名、手机号、岗位」 |
| 非必填 | 缺了不影响系统跑，仅资料不完整 | 性别、政治面貌、部门、证照扫描件等 |

> 原则：**先让系统能用，再让资料完整**。非必填项允许后续补充。

### 4.1 数据建模：主表 + 子表

核心档案（人员、车辆）采用**主表 + 子表**结构：

```
人员主表 person（基本信息）
  ├─ 人员证照子表 person_cert（驾驶证、从业资格证、身份证...）
  ├─ 劳动合同子表 person_contract
  └─ 人员档案子表 person_archive（一人一档）

车辆主表 vehicle（基本信息）
  ├─ 车辆证照子表 vehicle_cert（行驶证、营运证、登记证...）
  ├─ 车辆保险子表 vehicle_insurance
  └─ 车辆档案子表 vehicle_archive（一车一档）
```

> 优点：字段清晰、易扩展新证照类型、到期预警可统一扫描子表。

### 4.2 审批流：自建轻量审批引擎

自建一个通用审批引擎（不引入 Flowable/Activiti），支持：
- 多级审批（如制度评审的三级：安全科负责人 → 分管安全副总 → 总经理）
- 审批状态流转（待提交 / 审批中 / 通过 / 驳回）
- 抄送、会签

```sql
-- 审批核心表
CREATE TABLE flow_process (     -- 审批流程实例
  id, biz_type, biz_id, title, status, current_node, created_at
);
CREATE TABLE flow_node (        -- 审批节点
  id, process_id, node_order, approver_id, status, comment, approved_at
);
```

### 4.3 统一预警引擎

跨模块的「到期/逾期」提醒统一由一个预警引擎处理，不分散在各模块：

| 预警类型 | 数据来源 |
|---------|---------|
| 证照到期（人/车） | person_cert / vehicle_cert |
| 保险到期 | vehicle_insurance |
| 合同到期 | person_contract |
| 培训到期 | 培训模块 |
| 三检未完成 | 三检模块 |
| 隐患逾期 | 隐患模块 |

```
预警引擎：定时任务扫描 → 生成预警记录 → 推送两端首页 + 消息中心
```

### 4.4 全量操作日志（履职留痕）

关键操作（三检、整改、审批、删除、登录等）**全量记录**，满足「免责取证」：

```sql
CREATE TABLE sys_oper_log (
  id, user_id, tenant_id, module, action, target_id,
  before_data JSON, after_data JSON, ip, created_at
);
```

> **数据可改，日志不改**（重要原则）：操作日志全量留存、不可删改，作为审计凭据；但**业务数据本身允许超管修改**（见 4.5），两者不冲突——改了数据，日志会记录"谁在何时把什么改成了什么"，反而更完整地满足取证。

### 4.5 平台级超级管理员

- **定位**：平台运营方，跨企业
- **权限**：查看所有企业数据、**永远有修改所有企业数据和规则权限的能力**
- **与企业管理员的区别**：企业管理员只能管本企业；超管跨企业
- **纠错优先原则（用户确认）**：当前阶段以服务客户为主，客户操作失误导致记录出错时，超管能**人工改回**。监管端/过审的合规防篡改（如数据上链、签名锁死）后续再议，不在首期实现。

### 4.5.1 运营侧角色层级（渠道商模型，用户确认）

```
平台超级管理员（顶级，平台方自持）
   │  创建多个
   ▼
服务商账号（渠道商账号）
   │  服务
   ▼
运输企业（租户）
```

| 角色 | 层级 | 关键能力 |
|------|------|---------|
| **平台超级管理员** | 顶级 | 创建/管理服务商账号（渠道商）、全量数据 + 规则 + 纠错 |
| **服务商账号** | 渠道商 | 管理模板/视频库/题库等配置、**修改所有台账记录、录入即生成台账**、服务名下企业 |

> **服务商账号拥有修改所有台账记录的权限，可通过录入直接生成对应台账**（无需真实执行流程）。这是"代录"能力的本质，也是运营方为渠道企业提供的增值服务基础。平台超管通过创建多个服务商账号来发展渠道商。

### 4.6 部署与环境

| 项 | 结论 |
|----|------|
| 部署形态 | Docker 容器化（后端 + 前端 + 小程序编译产物 + Nginx 一个 compose 拉起） |
| 环境 | 三环境：dev（开发）/ test（测试）/ prod（生产） |
| 代码托管 | 私有 Git 仓库（GitHub/Gitee/工蜂） |

## 七、容量规划与扩展性设计

### 7.1 目标量级（已确认，2026-10-30 上调）

| 指标 | 前期 | 后期 |
|------|------|------|
| 企业数 | 100 家起 | 数百家 |
| 司机/从业人数 | 数千人（100 家企业 × 单家几十人） | 数万人 |
| 每企业人数 | 几十号人 | 几十~上百 |
| 并发特征 | 低频分散（三检/隐患/会议等）；**线上学习模块为高并发点，需支持 1000 人同时看视频** | 同左 |

> **并发重点变更（详见《00-产品定位与架构总纲》6.3）**：线上学习（视频点播）是唯一高并发压力点，采用 **CDN/对象存储分发**，源站不承载视频流量，仅处理鉴权 + 播放进度心跳（轻量请求）。其余业务模块仍为低频分散，单库 + Redis 足够。

### 7.2 结论

**当前技术架构支撑该量级，唯一需要额外设计的是线上学习的视频分发**。业务层（三检/隐患/会议/台账等）仍是低频分散场景，一台中等配置服务器（如 4C8G）+ Redis 即可扛住。**视频点播 1000 并发不占用源站**——走 CDN/对象存储分发（详见《00-产品定位与架构总纲》6.3）。真正的风险不在技术选型，而在以下「易埋坑点」是否设计正确。

### 7.3 五条扩展性铁律（后续所有模块必须遵守）

| # | 铁律 | 说明 | 违反后果 |
|---|------|------|----------|
| 1 | **模块化单体现先行** | 单体内部按模块清晰分包，后期按需拆微服务，代码不动 | 后期拆服务要重写 |
| 2 | **主键用雪花 ID，不带业务含义** | 为未来分库分表预留，不做自增主键 | 分表后主键冲突 |
| 3 | **热点数据走 Redis** | 菜单/权限/预警等高频读数据缓存，不每次查库 | 数据库被频繁打满 |
| 4 | **文件独立存储** | 证件照片/附件放 MinIO/OSS，不存数据库 | 数据库体积暴涨、备份慢 |
| 5 | **耗时操作异步化** | 预警扫描、报表统计用定时任务/队列，不阻塞用户 | 页面卡顿、接口超时 |
| 6 | **一切业务成果物皆可归档** | 每个业务模块保存数据时，同时登记归档项（带档案盒归属），保证系统成果物可生成 PDF 对应政府检查目录 | 政府检查时台账缺失、无法打印归档 |

### 7.4 扩容路线图（后期按需，非现在做）

| 阶段 | 用户量 | 动作 |
|------|--------|------|
| 现在 | 几千~几万 | 单体 + 单库 + Redis + 单服务器，够用 |
| 后期 | 几十万 | 拆服务（培训/监控等高频模块独立）+ 读写分离 + 分库分表 |
| 更后期 | 百万级 | 微服务 + 消息队列 + 分布式缓存集群 |

> 关键：**每张表、每个模块现在都按"能拆、能分"来设计**（雪花ID、模块分包、无状态服务），这样扩容只是"加机器/拆服务"，不推倒重来。

## 八、非功能性约束（汇总）

| 项 | 要求 |
|----|------|
| 多租户 | 字段级隔离，MyBatis-Plus 租户插件自动注入 |
| 权限 | RBAC（角色 + 菜单/按钮 + 数据范围） |
| 留痕 | 全量操作日志，不可篡改 |
| 预警 | 统一预警引擎，主动推送 |
| 等保 | 约二级等保 |
| 密码 | BCrypt 加密 |
| 文件 | 对象存储，证件/照片/附件 |
| 主键 | 雪花 ID，不带业务含义（为分库分表预留） |
| 缓存 | 菜单/权限/预警等热点数据走 Redis |
| 异步 | 预警扫描/统计等耗时操作异步化 |
