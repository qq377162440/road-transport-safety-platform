> 版本：v2.0（重新梳理产品定位）  
> 日期：2026-10-30  
> 状态：已确认（作为后续所有详细设计与原型的统一总纲）

---

## 一、产品一句话定位

面向**道路运输企业**（普货 / 危货 / 客运）的**安全生产管理系统**：企业用 PC 端 + 小程序端完成日常安全生产工作（培训、会议、隐患排查、一日三检、人车档案等），系统沉淀数据后**一键生成合规台账 PDF**，供打印纸质归档、接受政府检查。服务商通过「范本推送 + 代录」两种方式，快速服务大量客户。

## 二、三类客户与双端

### 2.1 客户范围（三类营运类型）

| 营运类型   | 简称     | 典型企业         | 本轮设计深度              |
| ------ | ------ | ------------ | ------------------- |
| 普通货物运输 | **普货** | 小微个体户、中小物流公司 | **详细设计 + 原型（当前主攻）** |
| 危险货物运输 | **危货** | 危化品运输企业      | **差异已落地（P0~P3 全部完成）** |
| 道路旅客运输 | **客运** | 客运班线、旅游包车    | **冻结（等用户明确再动）**        |

> **三类差异点（危货已落地，客运冻结）**：
>
> - **范本差异**：危货多押运员、装卸管理员、车辆技术管理员等岗位；制度/责任书/承诺书均有危货独立版本 ✅ 已落地。
> - **岗位差异**：普货 4 岗 / 危货 9 岗；客运有驾驶员、乘务员等 ⏸ 客运冻结。
> - **专项台账差异**：危货有「禁毒承诺书」、危险品运输台账、电子运单、装卸查验、押运员在岗 ✅ 已落地；客运班线、包车合同等 ⏸ 冻结。
> - **动态监控差异**：危货电子运单强制 ✅ 已落地；客运凌晨 2-5 时管控 ⏸ 冻结。
>
> **普货为主线，危货 P0~P3 差异增量已全部落地，客运整体冻结（等用户明确说"动客运"再动）**。架构、字段、范本引擎、台账引擎均按「三类可扩展」设计，危货接入无需推倒重来。详细差异见《21-危货客运差异与增量设计》。

### 2.2 双端定位

| 端          | 定位                   | 核心用户               | 核心动作               |
| ---------- | -------------------- | ------------------ | ------------------ |
| **PC 网页端** | 管理 + 台账 + 数据 + 服务商运营 | 企业管理员、安全员、法人、服务商账号 | 配置范本、看台账、生成 PDF、代录 |
| **微信小程序端** | 一线执行 + 填报 + 学习       | 驾驶员、押运员、管理人员       | 三检、签到、学习、拍照、签字     |

> 双端通过**统一 JWT 认证**打通，同一账号登录两端，数据实时同步。

## 三、双角色模型（企业 + 服务商）

这是本系统的核心骨架：**同一套系统，两类角色，两种价值**。

### 3.1 企业账号（客户侧）

| 角色       | 端        | 核心诉求    | 核心能力                  |
| -------- | -------- | ------- | --------------------- |
| 企业管理员    | PC       | 管好本企业安全 | 全部菜单 + 用户/角色管理 + 台账归档 |
| 法人/负责人   | PC + 小程序 | 全局把控    | 查看全局数据、审批、督办          |
| 安全员/管理人员 | PC + 小程序 | 干好日常安全  | 隐患、会议、培训、档案、台账        |
| 驾驶员/从业人员 | 小程序      | 快捷执行    | 三检、学习、签到、签字、查证照       |
| 押运员（危货）  | 小程序      | 快捷执行    | 同驾驶员（部分差异）            |

> 企业侧的核心价值：**用系统做完日常安全生产工作，数据自然沉淀，一键打印合规台账**，解决「人员分散、纸质台账难维护、政府检查被动」的问题。

### 3.2 服务商账号（运营侧）

| 角色                  | 核心诉求     | 核心能力                        |
| ------------------- | -------- | --------------------------- |
| **服务商账号**（= 运营方管理员） | 快速服务大量客户 | ① 起草范本并推送 ② 代录台账 ③ 系统配置管理   |
| 平台超级管理员             | 顶级管控     | 创建/管理服务商账号（渠道商）、全量数据 + 规则纠错 |

> **服务商账号的两大核心能力**（本产品区别于通用 SaaS 的关键）：

| 能力              | 说明                                                         | 适用客户             |
| --------------- | ---------------------------------------------------------- | ---------------- |
| **① 范本起草 + 推送** | 针对不同客户起草不同范本（制度、应急预案等静态资料），推送到企业。企业只需按清单完成任务（拍照、签字），即可完成台账 | 会用系统的客户          |
| **② 代录台账**      | 服务商上传照片 + **复用企业历史签字数据**（缺失才发起企业线上签字），选用合适范本，**无需推送给企业、直接生成完整台账** | 不会用系统的客户（小微普货为主） |

## 四、线上能力：解决人员分散 + 留痕

本系统的线上功能，本质是解决「运输企业人员高度分散、难以集中管理」的问题，核心是**三个线上化**：

| 能力                   | 解决的问题           | 留痕 → 台账                   |
| -------------------- | --------------- | ------------------------- |
| **远程签字**             | 人员分散，无法线下集中签字   | 每次签字留痕（谁、何时、签了什么），生成签字表归档 |
| **电子档归档**            | 纸质档案难保存、易丢失、难查询 | 所有证照、记录电子化，随时生成 PDF 打印    |
| **线上培训**（看视频 + 做题考核） | 司机分散，无法集中培训     | 学习时长、视频观看、考核成绩留痕，生成培训台账   |

> **核心逻辑**：**「系统做完 → 有留痕 → 可生成台账」**。这是贯穿全系统的铁律——任何线上动作都必须留痕，任何留痕都能归档成台账。

## 五、签约前的台账补齐（服务商增值服务）

客户在签约合作**之前**，台账往往非常不完善。接手后通常需要帮客户**补齐历史台账**。这是服务商账号「代录」能力的核心场景。

### 5.1 补齐逻辑

| 步骤       | 说明                                                                |
| -------- | ----------------------------------------------------------------- |
| ① 选范本    | 服务商从范本库选合适范本（**静态**：制度、应急预案、责任书、承诺书、任命书等；**动态**：培训、隐患排查、会议等记录类范本） |
| ② 上传照片+复用签字 | 服务商上传照片（培训/会议/隐患照片）；签字优先**读取企业历史签字数据自动复用**，缺失才需企业人员登录账号线上签 |
| ③ 生成台账   | 系统把照片、签字填入范本，快速生成**规范的一整套台账**                                     |

### 5.2 与「代录工作台」的关系

- 「服务商代录工作台」就是这一能力的**产品化入口**（已做原型 `quick_gen.html`）。
- 补齐的台账**回写**到对应企业的电子档案柜，企业随后也能看到、下载。

## 六、架构设计重估（重点：并发）

### 6.1 目标量级升级

> 原容量规划（00 文档 7.1）为「企业几十~几百、并发低频分散」。现按用户最新确认，**上调**：

| 指标      | 原规划   | 新目标                                            |
| ------- | ----- | ---------------------------------------------- |
| 服务企业数   | 几十~几百 | **100 家起，可扩展至数百家**                             |
| 司机/从业人数 | 几千~几万 | **100 家企业 → 数千司机**（单家几十人，按 100 家计 3000~5000 人） |
| 并发特征    | 低频分散  | **线上学习模块为高并发点，需支持 1000 人同时观看视频**               |

### 6.2 压力分析：谁是瓶颈

| 模块             | 压力等级      | 说明                         |
| -------------- | --------- | -------------------------- |
| **线上学习（视频点播）** | 🔴 **最高** | 1000 人同时看视频，是带宽 + 存储压力的集中点 |
| 台账 PDF 生成      | 🟡 中      | 批量生成走异步队列，压力可控             |
| 三检/隐患/会议等填报    | 🟢 低      | 低频分散，单库 + Redis 足够         |
| 远程签字           | 🟢 低      | 低频，留痕写库即可                  |

### 6.3 线上学习模块：1000 并发视频方案（关键）

**核心决策：视频点播走 CDN / 对象存储分发，不占用源站带宽。**

| 决策项  | 结论                                          |
| ---- | ------------------------------------------- |
| 视频存储 | 阿里云 OSS（或 MinIO 私有化）                        |
| 视频分发 | **CDN 加速**（OSS 开启 CDN，或接入 CDN 服务），用户从边缘节点拉流 |
| 视频转码 | 上传后转多码率（1080p/720p/480p），适配不同网络             |
| 防盗链  | OSS 私有 Bucket + CDN 鉴权（URL 签名，带时效），防盗链      |
| 学习留痕 | 前端定时上报播放进度（心跳），后端记录观看时长，判断是否学完              |
| 考核   | 学完 → 进入做题考核（题库随机抽题），成绩留痕                    |

**为什么 CDN 能扛 1000 并发**：

- 视频是**静态大文件**，CDN 边缘节点直接分发，源站（应用服务器）**完全不承载视频流量**。
- 1000 人同时看视频，压力分散到 CDN 边缘节点，源站只处理「鉴权 + 播放进度上报」这类**轻量 HTTP 请求**（1000 并发的心跳请求，单机 Spring Boot + Redis 轻松扛住）。
- 应用服务器的数据库压力，也仅是「每秒几次~几十次的学习进度写入」，远低于视频流本身。

**容量估算（1000 并发看 720p 视频）**：

| 项          | 估算                                     |
| ---------- | -------------------------------------- |
| 单路 720p 码率 | 约 1~1.5 Mbps                           |
| 1000 路并发带宽 | 约 1~1.5 Gbps（**全部由 CDN 承担**，源站 0 压力）   |
| 源站需处理      | 仅鉴权请求 + 进度心跳，约 1000~2000 QPS 轻量请求，单机可扛 |
| 存储         | 视频按 500MB/小时计，课程库需预留 OSS 空间（成本极低）      |

### 6.4 架构演进路线

| 阶段 | 量级                        | 架构                                            |
| -- | ------------------------- | --------------------------------------------- |
| 现在 | 100 企业 / 数千司机 / 1000 并发学习 | **单体模块化 + CDN 分发视频 + 单库 + Redis + MinIO/OSS** |
| 中期 | 数百企业 / 数万司机               | 学习模块独立成服务 + 读写分离 + 分库分表（按需）                   |
| 后期 | 更大规模                      | 微服务 + 消息队列 + 分布式缓存集群                          |

> **关键原则不变**（沿用 00 文档七条扩展性铁律）：雪花 ID、模块化分包、文件独立存储、耗时异步化、**一切成果物可归档**。学习模块从第一天起就按「能独立拆服务」设计（清晰边界、无状态、进度上报异步化），避免后期拆分重写。
