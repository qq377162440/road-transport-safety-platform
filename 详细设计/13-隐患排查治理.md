# 详细设计 13 —— 隐患排查治理

> 所属域：danger（隐患排查治理）
> 优先级：**P0 保命功能**（安全分"隐患闭环率"占 30%，权重最高）
> 对应原系统：archive 子系统「隐患排查治理」（逆向报告 3.3）
> 上游依赖：11 一日三检（三检异常流转）、02 预警引擎（未闭环提醒）、08 台账归档（盒·风险分级管控与隐患排查治理）
> 下游被依赖：企业安全分（隐患闭环率）、08 归档引擎

---

## 一、模块定位

隐患排查治理是"责任闭环链"的**关键节点**——对应需求文档的因果链"人的不规范行为 → 隐患积累 → 事故"。隐患闭环率在企业安全分中占 **30%（最高权重）**，直接决定"不出事"。

**核心目标**：把"发现隐患 → 整改 → 验收销号"做成**线上全流程闭环**，任何一个隐患不闭环都会被系统盯住、被督办。

**统一视角**：隐患按"发现频次/维度"分形态——**日级别的三检异常、定期专项检查、随手发现上报**，本质都是隐患，统一闭环治理。一日三检就是**每天对车辆做的一次隐患排查**。

**边界**：本模块只做"隐患排查治理"（动态、事中）。**风险辨识**（静态、事前，对应逆向报告 3.6）是独立业务，虽然和隐患在档案盒里同属一盒，但模块上分开，后续单独设计。

## 三、隐患闭环模型（核心）

### 3.1 状态机（一条隐患的生命周期）

```
发现隐患 → 待整改 → 整改中 → 待验收 → 已闭环
                ↓                    ↓
            超期未整改           验收不通过 → 退回整改中
                ↓
            督办提醒（反复）
```

| 状态 | 含义 | 触发 |
|------|------|------|
| `待整改` | 隐患已登记，等待下发整改 | 隐患登记后 |
| `整改中` | 已下发整改通知，责任人在处理 | 下发整改后 |
| `待验收` | 责任人提交整改凭证，等验收 | 整改反馈后 |
| `已闭环` | 验收通过，隐患销号 | 验收通过后 |
| `超期` | 超过整改期限未闭环 | 到期未闭环（自动标记） |

### 3.2 排查类型体系（H5，完整字典）

> **关键洞察（用户确认）**：一日三检的异常流转，本质就是**日级别的隐患排查**。在此基础上，隐患排查有一套**完整的排查类型体系**，覆盖日常到专项的各种频次和维度。

| 排查类型 | 编码 | 频次 | 维度 | 说明 |
|---------|------|------|------|------|
| 一日三检异常 | check_daily | 每天 | 车辆 | 日级别隐患排查（司机三检报修） |
| 司机随手上报 | driver_report | 随时 | 任意 | 司机随时发现的隐患 |
| 月度全面隐患排查 | monthly_full | 每月 | 企业全面 | 每月一次的全面排查 |
| 月度重大事故隐患排查（专项） | monthly_major | 每月 | 重大事故隐患 | 专项排查重大事故隐患 |
| 重大节假日前隐患排查 | holiday_pre | 节假日前 | 企业全面 | 重大节假日前专项排查 |
| 应急物资排查 | emergency_supply | 定期 | 应急物资 | 应急物资/器材/设备排查 |
| 汛期/暑期重大风险隐患排查 | season_risk | 汛期/暑期 | 重大风险 | 季节性重大风险专项排查 |
| 其他专项/日常检查 | other_plan | 按需 | 自定义 | 企业自定义的其他排查 |

> 所有排查类型统一汇入 `danger_record`，用 `check_type` 区分，闭环流程完全一致。**三检异常 = 日级别隐患排查**，是整套排查体系中频次最高、维度最聚焦车辆的一种。

### 3.3 闭环要素完整（H7）

一条隐患的完整闭环，必须记录以下**五类要素**（对应档案盒检查时的完整字段链）：

| 要素 | 字段 | 来源 |
|------|------|------|
| **隐患情况** | 隐患描述、等级、位置、照片/语音 | 发现时记录 |
| **检查人** | finder_id（发现人/检查人） | 排查执行人 |
| **整改情况** | 整改要求、整改反馈、凭证照片 | 整改环节 |
| **整改人** | responsible_id（整改责任人） | 下发整改时指定 |
| **验收人** | acceptor_id（验收人） | 验收环节 |

## 四、数据模型（DDL）

### 4.1 隐患排查记录主表 danger_record

```sql
CREATE TABLE danger_record (
  id              BIGINT PRIMARY KEY,
  tenant_id       BIGINT NOT NULL,
  check_type      VARCHAR(30) NOT NULL,        -- 排查类型（见 3.2 字典：check_daily/monthly_full/monthly_major/holiday_pre/emergency_supply/season_risk/other_plan/driver_report）
  ref_id          BIGINT,                      -- 来源ID（如 check_record.id，三检异常时）
  title           VARCHAR(200),                -- 隐患名称/描述（隐患情况）
  danger_level    VARCHAR(10),                 -- 隐患等级：一般/较大/重大
  location        VARCHAR(200),                -- 隐患位置（车辆/场地/设备）
  vehicle_id      BIGINT,                      -- 关联车辆（若为车辆隐患）
  finder_id       BIGINT,                      -- 检查人/发现人
  find_time       DATETIME,                    -- 发现时间
  photos          VARCHAR(2000),               -- 照片（JSON，多张）
  voice_url       VARCHAR(500),                -- 语音（若来自三检报修）
  status          VARCHAR(20) DEFAULT 'pending', -- pending待整改/rectifying整改中/verify待验收/closed已闭环/overdue超期
  created_at      DATETIME DEFAULT NOW(),
  updated_at      DATETIME,
  deleted         TINYINT DEFAULT 0
);
```

### 4.2 整改单子表 danger_rectify（H6：排查发现问题联动生成）

```sql
CREATE TABLE danger_rectify (
  id              BIGINT PRIMARY KEY,
  tenant_id       BIGINT NOT NULL,
  danger_id       BIGINT NOT NULL,             -- 关联 danger_record
  rectify_no      VARCHAR(50),                 -- 整改单编号（联动生成）
  rectify_require VARCHAR(500),                -- 整改要求
  responsible_id  BIGINT,                      -- 整改人（整改责任人）
  deadline        DATETIME,                    -- 整改期限
  rectify_note    VARCHAR(500),                -- 整改情况说明
  rectify_photos  VARCHAR(2000),               -- 整改凭证照片
  submit_time     DATETIME,                    -- 整改反馈提交时间
  created_at      DATETIME DEFAULT NOW()
);
```

> **联动生成（H6）**：排查时发现问题（`status` 进入 `pending`），系统**自动生成整改单** `danger_rectify`（含整改单编号），无需安全员手动新建。整改单承载"整改要求 + 整改人 + 期限 + 整改情况"，是闭环的中间载体。

### 4.3 验收记录子表 danger_accept

```sql
CREATE TABLE danger_accept (
  id              BIGINT PRIMARY KEY,
  tenant_id       BIGINT NOT NULL,
  danger_id       BIGINT NOT NULL,
  acceptor_id     BIGINT,                      -- 验收人（安全员）
  accept_result   VARCHAR(10),                 -- pass通过/reject退回
  accept_note     VARCHAR(500),                -- 验收意见
  accept_time     DATETIME,
  created_at      DATETIME DEFAULT NOW()
);
```

### 4.4 隐患整改台账（对应档案盒归档项）

> 档案盒「风险分级管控与隐患排查治理」（普货盒八 / 危货盒九）中，隐患相关的两条归档项：
> 1. **隐患排查记录**（排查内容、照片、签字）
> 2. **隐患排查治理**（整改通知书、验收单）

这两条由 `danger_record` + `danger_rectify` + `danger_accept` 汇总生成，归档时自动登记到 08 归档引擎。

### 4.5 排查清单模板表 danger_check_template（H8，系统级范本）

```sql
CREATE TABLE danger_check_template (
  id              BIGINT PRIMARY KEY,
  tenant_id       BIGINT NOT NULL DEFAULT 0,   -- 0=系统级范本，>0=企业自定义
  template_name   VARCHAR(100) NOT NULL,       -- 清单名称（如"月度全面隐患排查清单"）
  check_type      VARCHAR(30) NOT NULL,        -- 适用排查类型（见 3.2 字典）
  item_list       TEXT,                        -- 排查项目清单（JSON：项目名称+说明+判定方式）
  is_default      TINYINT DEFAULT 0,           -- 是否该类型默认清单
  created_at      DATETIME DEFAULT NOW(),
  updated_at      DATETIME
);
```

> **系统级范本（H8）**：
> - 系统预置一套排查清单范本（`tenant_id=0`），按排查类型区分——月度全面、重大事故隐患、节假日、应急物资、汛期暑期各有对应清单。
> - **创建排查时选用**：安全员发起排查时，选择排查类型 → 自动带出该系统级清单范本，可在此基础上增删项目。
> - **企业自定义**：企业可复制系统范本为 `tenant_id=企业ID` 的定制版，覆盖系统默认（沿用 09 范本引擎"系统级→企业级"的三层思路）。

### 4.6 系统级排查清单范本内容（线下台账比对预置）

> 线下成品"佛山普货隐患排查（月度及重大事故隐患）"的排查表列结构为：**序号 / 项目类别 / 检查项目 / 检查内容与检查标准 / 检查结果 / 备注**，其中"项目类别"分两大类——**重大事故隐患排查项** + **基础管理**。系统预置清单按此结构，重点预置下列**重大事故隐患专项排查项**（政府重点检查，须固化）：

| 类别 | 检查项目 | 检查内容与检查标准 |
|------|---------|-------------------|
| 重大事故隐患排查项 | 特殊天气 | 经营地或运营线路途经地已发布台风橙色及以上预警，暴雨、暴雪、冰雹、大雾、沙尘暴、大风、道路结冰红色预警，或地质灾害气象风险红色预警等不具备安全通行条件时，是否执行政府部门停运指令或企业应急预案要求仍擅自安排运输作业 |
| 重大事故隐患排查项 | 企业资质 | 是否存在未取得经营许可或未按规定进行备案从事经营活动，或超出许可（备案）事项和有效期经营的情况 |
| 重大事故隐患排查项 | 三超一疲劳 | 所属经营性驾驶员和车辆是否存在长期"三超一疲劳"（超速、超员、超载、疲劳驾驶）且运输过程中未及时提醒纠正、运输行为结束后一个月内未严肃处理，或所属经营性驾驶员存在一次计10分及以上诚信考核计分情形且未严肃处理仍继续安排上岗作业 |
| 重大事故隐患排查项 | 车辆运输 | 所属货运车辆是否故意夹带危险货物或违规运输禁运、限运物品，且运输过程中未及时提醒纠正、运输行为结束后一个月内未严肃处理 |
| 重大事故隐患排查项 | 车辆运输 | 所属货运车辆运输过程中是否违法装载导致车货总质量超过100吨 |
| 重大事故隐患排查项 | 车辆改装 | 是否使用报废、擅自改装、拼装、检验检测不合格（含未在有效期内）以及其他不符合国家规定的车辆装备、设施设备等从事经营活动 |
| 基础管理 | 安全会议管理 | 企业安全生产例会是否按制度召开，有会议记录（会议通知、参会人员签到、会议内容材料、会议照片等） |
| 基础管理 | （其余按排查类型增补） | 培训、三检、动态监控、应急物资等基础管理项 |

> **重大事故隐患项 vs 基础管理**：重大事故隐患项是"一票否决"类（触犯即重大隐患，须立即停业整改），基础管理项是常规检查项。系统在排查清单范本中**分两类展示**，排查结果对重大隐患项做高亮提醒。

## 五、核心流程

### 5.1 隐患发现（按排查类型）

```
① 三检异常（日级别）：司机三检报修 → 自动生成 danger_record（check_type=check_daily）
   带出：车牌、司机、异常项、语音、照片、发现时间

② 定期专项排查（PC 发起）：安全员发起排查，选择排查类型
   → 自动带出该类型的系统级排查清单范本（H8，可增删项目）
   - 月度全面隐患排查（monthly_full）
   - 月度重大事故隐患排查（monthly_major）
   - 重大节假日前隐患排查（holiday_pre）
   - 应急物资排查（emergency_supply）
   - 汛期/暑期重大风险隐患排查（season_risk）
   → 排查项目逐项判定 → 有问题登记为 danger_record（自动联动生成整改单）

③ 司机随手上报（driver_report）：小程序"隐患上报" → 隐患描述（语音/拍照/点选）
   → danger_record
```

### 5.2 闭环流程（H3/H6/H7，全流程 + 联动 + 完整要素）

```
发现隐患（记录"隐患情况"+"检查人"）
  → 自动联动生成整改单（H6）
  → 安全员下发整改（指定"整改人"+期限+要求）
  → 整改人整改（小程序反馈：上传整改凭证，记录"整改情况"）
  → 安全员验收（"验收人"验收，通过→闭环 / 退回→继续整改）
  → 超期未闭环 → 自动督办提醒（预警引擎）
```

> **闭环五要素全程留痕（H7）**：隐患情况、整改情况、检查人、整改人、验收人，五个要素在闭环各环节自动记录，形成完整字段链，满足档案盒检查。

### 5.3 督办机制

- **超期提醒**：隐患超过整改期限未闭环，预警引擎分级提醒（临期/超期）
- **未闭环盯梢**：所有非 `closed` 状态的隐患，在安全员"今日待办"里持续出现
- **闭环率统计**：`closed 数量 / 总数量`，计入企业安全分（30% 权重）

## 六、业务规则

1. **排查类型统一**：三检异常（日检）/ 五类定期专项 / 司机上报，统一汇入 `danger_record`，闭环流程一致。
2. **状态流转**：待整改 → 整改中 → 待验收 → 已闭环；超期自动标记，验收退回则回到整改中。
3. **联动生成整改单（H6）**：排查发现问题（进入 `pending`）时，系统自动生成整改单，无需手动新建。
4. **闭环五要素（H7）**：隐患情况、整改情况、检查人、整改人、验收人全程留痕，缺一不可。
5. **超期督办**：超过 `deadline` 未闭环，预警引擎分级提醒，记录督办次数。
6. **整改留痕**：整改凭证（照片/语音）、验收意见、时间、人员全程留痕；超管可纠错（H4）。
7. **闭环率**：`closed / total`，计入企业安全分（权重 30%，可配置）。
8. **三检异常自动建单**：三检报修 `result=abnormal` 自动生成隐患单 + 整改单，无需二次录入。
9. **归档对齐**：隐患记录（含排查类型）+ 整改通知书 + 验收单，自动登记到 08 归档引擎「盒·风险分级管控与隐患排查治理」。

## 七、页面交互设计

### 7.1 PC 端（管理端，核心）

- **列表页**（对齐原型 `pc/danger.html`）：检查名称、检查时间、排查类型、检查项目、整改项、状态、操作
- **隐患详情**：隐患描述 + 照片/语音 + 整改记录 + 验收记录 + 状态流转时间线 + 闭环五要素（检查人/整改人/验收人）
- **发起排查**：选择排查类型 → **自动带出系统级排查清单范本**（可增删项目），逐项判定，发现问题自动联动生成整改单
- **清单模板管理**：查看/维护系统级排查清单范本，支持企业自定义覆盖
- **整改下发**：指定整改责任人 + 期限 + 要求（联动生成的整改单自动带入）
- **验收**：查看整改凭证，通过/退回
- **督办看板**：未闭环隐患列表，超期高亮

### 7.2 小程序（司机端）

- **隐患上报**：发现隐患 → 拍照/语音/点选 → 提交
- **整改反馈**：收到整改任务 → 完成整改 → 上传凭证照片/语音 → 提交

## 十、开发任务拆解

1. 建表（danger_record / danger_rectify / danger_accept / danger_check_template）
2. 排查类型字典初始化（日检/月度全面/月度重大事故隐患/节假日/应急物资/汛期暑期/司机上报）
3. 排查清单模板初始化（系统级范本，按排查类型区分）
4. 隐患登记（各排查类型统一入口）
5. 发起排查时自动带出系统级清单范本（支持增删 + 企业自定义）
6. 三检异常 → 隐患自动建单（联动 11 模块）
7. 排查发现问题 → 自动联动生成整改单（H6）
8. 闭环状态机（待整改→整改中→待验收→已闭环/超期）
9. 整改下发 + 反馈 + 验收（闭环五要素留痕）
10. 督办机制（超期提醒，预警引擎接入）
11. 闭环率统计（企业安全分联动）
12. PC 列表 + 详情 + 督办看板（含排查类型筛选）
13. 小程序隐患上报 + 整改反馈
14. 隐患记录 → 08 归档引擎登记（排查记录/整改通知/验收单）

## 十一、验收标准

1. 三检异常能自动生成隐患单 + 整改单，带出车牌/司机/异常项/语音/照片，无需二次录入。
2. 支持五类定期专项排查：月度全面、月度重大事故隐患、重大节假日前、应急物资、汛期/暑期重大风险。
3. 创建排查时能选择系统级排查清单范本，并按排查类型自动带出对应清单，支持增删项目和企业自定义。
4. 排查时发现问题自动联动生成整改单，闭环流程一致。
5. 闭环五要素（隐患情况、整改情况、检查人、整改人、验收人）全程留痕，缺一不可。
6. 隐患能从"待整改"一路流转到"已闭环"，超期自动标记并督办。
7. 闭环率实时统计，计入企业安全分（30% 权重）。
8. 隐患记录 + 整改通知书 + 验收单能自动归档到「盒·风险分级管控与隐患排查治理」。
