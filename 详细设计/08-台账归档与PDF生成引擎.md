# 台账归档与 PDF 生成引擎（贯穿全系统的核心基础设施）

> 版本：v2.0
> 日期：2026-10-27
> 状态：已确认
> 优先级：P0（这是整个系统的**产品定位核心**，不是附属功能）

---

## 一、产品定位：系统存在的目的

### 1.0 一句话定位

> **本系统的目的，就是作为一个工具，高效、全面、专业地帮助客户满足政府安全检查。**

这不是一个"功能模块"，而是**整个系统存在的理由**。所有业务模块（隐患、培训、三检、会议、监控……）都是为"最终生成一套经得起检查的台账"服务的。

### 1.1 为什么这是"核心基础设施"

政府检查道路运输企业时，按一套**固定目录**逐项核验企业的安全生产台账。这套目录就是企业台账的**归档分类逻辑**。

> 用户原话（关键需求）：
> "这是政府检查企业的时候的目录，也是企业台账归档分类逻辑。我们系统生成的所有资料都要能够生成 PDF 以便打印归档，一一对应政府的检查。这个东西你要贯穿整个项目开发。"

**核心命题**：系统里每个业务模块产生的数据/表单/记录，最终都要能落到某个"档案盒"里，并以**可打印的 PDF** 形式输出，供企业打印后装进实体档案盒，接受政府检查。

### 1.2 三个设计目标

| 目标 | 含义 |
|------|------|
| **高效** | 客户用最小投入（少打字、少手工整理）就能产出合规台账 |
| **全面** | 政府目录里每一项，系统都能对应产出，不漏项 |
| **专业** | 台账格式、内容、流程符合法规要求，经得起检查 |

## 二、三大类资料（核心分类逻辑，统领全系统）

> 这是理解整个系统的**第一性原理**。政府目录里的所有资料，按"谁来生产、怎么生产、何时更新"分成三大类。每一类对应**完全不同的系统生产方式**。

### 2.1 三类资料总览

| 代号 | 类别 | 定义 | 典型资料 | 谁来生产 | 系统角色 | 更新频率 |
|------|------|------|---------|---------|---------|---------|
| **A** | 静态资料 | 制度、预案、责任书等**范本类** | 制度汇编、应急预案、安全生产责任书、承诺书、岗位危害告知书 | 系统从范本生成 → 人员签字确认（模板因地区/规模选不同范本套） | **生成器**（模板/范本引擎） | 一般每年一次 |
| **B** | 动态资料 | 隐患、培训、三检等**工作记录** | 隐患排查记录、培训记录、一日三检、会议记录、费用使用台账 | 客户在小程序端**执行工作**产生；服务商可代录/提取签字照片直接生成 | **记录器**（采集执行过程） | 随工作完成周期更新 |
| **B** | 动态资料·上传留存子型 | 动态监控台账等**外部平台产出** | 动态监控工作记录台账、设备故障异常台账、在线率/月报台账、交警抄报 | 外部动态监控平台/交警抄报产生，**本系统只上传留存**（动态监控不归本系统管） | **留存器**（上传 + 留存 + 违规识别） | 按周期上传留存 |
| **C** | 证件资料 | 营业执照、人车证件、备案回执、产权证明等**证照/凭证** | 营业执照、经营许可证、行驶证、驾驶证、从业资格证、保险单、备案回执、产权证明 | 客户**手动上传** | **看管器**（缺失+到期预警） | 按证照有效期 |

> **A/B/C 三码权威定义（2026-11-12 定稿）**：原「②′ 上传留存资料」不再作为独立第四类，按性质拆分——外部平台台账归 **B**（动态资料·上传留存子型），备案回执/产权证明等证照归 **C**。完整规范与全量归档项映射见《详细设计/档案资料A-B-C分类规范.md》。

### 2.1.1 归档项更新频率（关键：不是所有资料都"每年一次"）

> 归档项必须区分**更新频率 / 有效期**，否则无法做到期预警、也无法判断「历史签字能否复用」。核心差异：

| 更新频率 | 典型归档项 | 规则 |
|---------|-----------|------|
| **一年一签** | 安全生产责任书、承诺书、禁毒承诺书（危货） | 每年重新签订；**按自然年度算，每年 1 月 1 日需重签**；**代录时复用签字须核对签字年份**，跨年不能直接复用 |
| **入职一次** | 岗前三级教育培训、岗位危害告知书 | 入职签一次；换岗/复工需重训重签 |
| **每月一次** | 岗中培训（月度培训）、月度会议、隐患排查、费用使用台账 | 按月生成，缺月即缺项 |
| **每季度一次** | 安全生产领导小组会议 | 每季度一次 |
| **年度一次** | 培训计划、应急演练计划、风险辨识清单、年度考核 | 每年一次 |
| **按证照有效期** | 营业执照、经营许可证、驾驶证、从业资格证、责任险保单、罐体检测 | 到期预警，换证重传 |
| **每日/每趟** | 一日三检、动态监控台账、危货电子运单 | 每日/每趟登记 |
| **有变动时更新** | 组织架构、任命书、领导小组通知、制度汇编、风险告知卡 | 非周期，变更即更新 |
| **三年一次修订** | 应急预案 | 法定周期（或重大变化时） |

> **系统落点**：
> - `archive_catalog` 表新增 `renew_freq` 字段（YEARLY/MONTHLY/QUARTERLY/ONCE/ONCHANGE/DAILY/TRIP/CERT/LONG），作为归档项目录的静态属性。
> - 预警引擎对「一年一签」类归档项按**自然年度**判断：记录签署年度 `signed_year`，**签署年度 < 当前自然年度（即跨年）→ 每年 1 月 1 日需重新签订**；不按"签署日期+365天"计算。
> - 服务商代录「复用历史签字」时，对 `renew_freq=YEARLY` 的文件**校验签字年份**，跨年提示重新签。


### 2.2 三类资料的完整生产链路

```
① 静态资料（范本生成）
  收集关键信息（企业/人员/岗位）
    → 系统套用范本，生成台账
    → 人员签字确认（小程序/线下）
    → 生成 PDF 归档
    → 年度到期提示更新

② 动态资料（工作记录）
  客户在小程序端执行工作（三检/培训/隐患...）
    → 系统实时记录执行过程
    → 自动汇总生成台账
    → 生成 PDF 归档
    → 随每次工作完成累积

③ 证件资料（手动上传）
  客户上传证照（拍照/扫描）
    → OCR 识别关键字段 + 到期日
    → 缺失项 + 到期项 → 统一预警
    → 手动更新新证照
```

### 2.2.1 动态资料的两种生成方式（核心设计）

动态资料（②）必须支持**两种生成方式**，这是系统能否真正被客户用起来的关键：

| 维度 | 方式一：真实流程 | 方式二：先台账后执行 |
|------|----------------|---------------------|
| **操作人** | 客户一线人员（司机/安全员） | **服务商账号**（代录功能，见 01 文档 3.2） |
| **时序** | 先执行 → 后台账 | 先出账 → 后补执行 |
| **采集物** | 系统实时留痕（时间、GPS、现场照片） | 线下照片 + 签字（运营人员代采） |
| **适用场景** | 日常正常运营 | 历史补账、检查前突击、客户不熟悉系统 |
| **本质** | 记录已发生的真实工作 | 帮客户"补台账"，线下再执行 |

**两种采集方式（方式二内部，两种都要）**：

```
方式二-A：线上代录
  运营人员在 PC 端录入台账字段（时间/内容/参与人）
    → 客户线下完成后，拍照签字页/现场照片上传
    → 运营人员补传照片 → 生成台账 PDF

方式二-B：小程序现场采集
  运营人员用小程序到现场
    → 拍客户签字、拍现场照片
    → 当场生成台账 PDF
```

**关键设计约束（已确认）**：

1. **权限收口**：方式二只能由**服务商账号的代录功能**操作，普通客户账号没有"先台账后执行"的入口。这既防止客户自己随意造假，也把"帮客户补账"变成运营方提供的**增值服务**。
2. **打印件完全一致**：方式二生成的台账 PDF 与方式一**外观完全一致**，客户拿去检查看不出区别。补录与否只在系统内部标记，打印件不体现。
3. **台账即终点**：方式二生成台账后就结束，系统不追踪客户线下是否补做、不做"未补做"预警。线下执行由客户自行负责。

> **为什么需要方式二（产品动机）**：大量中小运输企业日常根本没有规范台账习惯，政府检查却要看台账。如果系统强制"先做流程才有台账"，客户会因"补不齐历史台账"而弃用。方式二是**降低客户启用门槛的过渡通道**，让客户先拿到合规台账应付检查，再逐步引导到方式一的真实流程。

### 2.2.2 方式二 = 增值服务（商业模式定位）

> 方式二不仅是技术功能，更是**运营方的核心增值服务与收入来源**。

| 维度 | 说明 |
|------|------|
| **定位** | "帮客户补台账"是一项**收费增值服务**，由运营方代劳 |
| **客户价值** | 不会用系统、没时间、补不齐台账时，花钱买省心 |
| **运营方价值** | 获客抓手 + 深度绑定 + 持续现金流（从"卖软件"升级为"卖服务"） |
| **收费模式（待定）** | 按次 / 按台账包 / 按企业年费（需后续单独设计计费模块） |
| **与方式一的关系** | 方式一是"自助"，方式二是"代劳"；理想路径是先代劳获客，再引导客户自助 |

**产品设计含义**：

1. **服务订单化**：方式二的每次代录应能形成"服务单"，记录为哪家企业、补了什么台账、耗时、收费，便于运营方结算与对账。
2. **引导自助**：在方式二服务过程中，可顺带引导客户开通方式一（自助流程），把"付费代劳"转化为"自主使用"。
3. **计费模块预留**：后续需独立设计"增值服务计费/订单/结算"模块（建议单列，不混入归档引擎）。本文档仅约定"方式二可被计价"这一事实，计费细节另立文档。

### 2.2.3 计费模块归属与续费路径（已确认）

> 计费模块**挂在超级管理员账号下**管理，客户续费走**双通道**。

**计费管理端**：平台级超级管理员账号（见《00-系统架构设计文档》4.5）负责管理所有企业的计费、开通、续费。

**客户续费双通道**：

| 通道 | 方式 | 流程 |
|------|------|------|
| **线上自助** | 客户自主扫码续费 | 客户扫码支付 → 系统自动开通/续期 → 即时生效 |
| **线下人工** | 转账给运营方，超管开通 | 客户转账 → 运营方收款确认 → 超管在后台手动开通/续期 |

**设计要点**：

1. **扫码续费**：客户端（PC/小程序）展示收款二维码，客户扫码支付后，系统通过支付回调自动开通/续期，无需人工干预。
2. **超管手动开通**：线下转账的客户，由超管在后台录入"已收款 + 开通/续期时长"，手动激活。
3. **统一到期管理**：两条通道最终都落到同一套"企业服务到期时间"，由统一预警引擎在到期前提醒客户续费。

> **待办**：增值服务的计费/订单/结算机制需单独出详细设计（独立模块，含扫码支付、超管手动开通、到期预警），不在归档引擎范围内展开。



### 2.3 三类资料的差异本质（为什么必须分开设计）

| 维度 | ① 静态 | ② 动态 | ③ 证件 |
|------|--------|--------|--------|
| 数据来源 | 范本 + 客户关键信息 | 小程序执行动作 | 客户上传文件 |
| 是否需要"执行行为" | 否（签字即完成） | **是**（必须真实执行） | 否 |
| 系统核心能力 | 范本管理 + 字段填充 + 签字 | 执行流程采集 + 台账汇总 | OCR + 到期预警 |
| 缺失后果 | 检查缺项 | 检查缺项 + **违法违规风险** | 检查缺项 + 资质失效 |
| 典型问题 | 范本不齐全、不更新 | 造假、补台账 | 证照过期未发现 |

> **关键洞察**：②动态资料是系统的**护城河**——方式一靠"真实执行工作"产生，自动留痕，无法事后批量造假；方式二则提供了"先台账后执行"的过渡通道，降低客户启用门槛。两种方式并存，既守住"真实留痕"的价值，又不把"不会用系统/需补台账"的客户拒之门外。

### 2.4 三类资料与档案盒的关系

政府目录的每个档案盒，内部资料**混含三类**。归档模型必须能同时承载三种生产方式：

| 档案盒 | ①静态 | ②动态 | ③证件 |
|--------|------|------|------|
| 一、公司档案及管理层档案 | 制度、责任书、承诺书、成立通知、复工复产方案 | 年度责任制考核 | 营业执照、经营许可证、责任险 |
| 二、制度及操作规程 | 制度汇编、法规清单 | — | — |
| 三、安全生产会议 | — | 会议记录（记录+签到+照片） | — |
| 四、培训教育 | 培训计划 | 培训记录（内容+照片+签字） | — |
| 五、安全费用 | 提取标准及计划 | 使用台账 | 营收证明、发票 |
| 六、动态监控 | — | 每日台账、违规教育 | — |
| 八、应急管理 | 应急预案、值班制度 | 演练、培训记录 | 备案回执 |
| 九、风险管控+隐患 | 风险辨识手册、告知卡 | 隐患排查记录、整改 | — |
| 十、一日三检 | — | 三检记录 | — |
| 十一、事故档案 | — | 事故资料、快报 | — |

### 2.5 归档项产出方式三原则（贯穿全系统，用户确认）

> 无论哪类资料、哪个档案盒，**每项目录最终都必须"有实物"装盒、能过政府检查**。实物产生方式只有三种：

| 产出方式 | 含义 | 系统动作 |
|---------|------|---------|
| **① 系统生成** | 系统里有数据 → 直接产出最终 PDF | 自动 |
| **② 企业自备** | 证件/保单/检验报告等实物 → 企业扫描上传 | 上传 |
| **③ 打印手写** | 系统里**没有数据** → 打印**空白表头/格式**，提示企业手写补充 | 打印空白模板 |

> **降级规则**：凡"登记表/记录表"类归档项，系统先查对应业务模块有无数据——**有数据→生成成品 PDF；无数据→打印空白格式表，提示"该表无系统数据，请打印后手写补充"**。证件类（②）不适用降级，必须上传实物。

> 此原则已落实到 07（一人一档）与 10（一车一档）的 `source_type` 字段枚举：`auto`（系统生成）/ `upload`（企业自备）/ `print`（打印手写）。

## 四、核心设计：三层归档模型

### 3.1 模型总览

```
┌─────────────────────────────────────────────────────────┐
│  档案盒目录（ArchiveCatalog）—— 按营运类型模板化        │
│  "政府检查目录"的数字化，一级盒 → 二级子项               │
└───────────────────────┬─────────────────────────────────┘
                        │ 归属关系
┌───────────────────────▼─────────────────────────────────┐
│  归档项（ArchiveItem）—— 具体某一条"资料/记录"          │
│  例：某次会议记录、某辆车的一日三检、某人的责任书        │
└───────────────────────┬─────────────────────────────────┘
                        │ 生成
┌───────────────────────▼─────────────────────────────────┐
│  PDF 成品（ArchivePdf）—— 可打印的归档文件              │
│  带统一版式：企业名、盒号、归档项、时间、二维码          │
└─────────────────────────────────────────────────────────┘
```

### 3.2 三层说明

| 层 | 数据表 | 说明 | 举例 |
|----|--------|------|------|
| **目录层** | `archive_catalog` | 档案盒分类，按营运类型模板预置 | "六、动态监控及交通违法管理" |
| **归档项层** | `archive_item` | 业务模块产生的"可归档成果物" | 某天的动态监控台账记录 |
| **成品层** | `archive_pdf` | 实际生成的 PDF 文件 | `监控台账_2026-10-27.pdf` |

### 3.3 关键机制：业务数据 ↔ 归档项 的自动绑定

**核心思想**：不是让用户手动"往档案盒里塞文件"，而是**业务模块产生数据时，自动登记为某个归档项**。

```java
// 伪代码：业务模块保存时，同时登记归档项
@ArchiveRegister(catalogCode = "MONITOR_DAILY")   // 注解声明归档归属
public void saveMonitorRecord(MonitorRecord record) {
    monitorMapper.insert(record);
    // 框架自动：archive_item 登记一条 "动态监控工作情况记录台账(每日)"
}
```

这样，**任何业务数据天然知道自己属于哪个档案盒**，归档不再依赖人工记忆。

## 五、数据库设计（DDL）

### 4.1 档案盒目录表（按营运类型模板化）

```sql
CREATE TABLE archive_catalog (
  id            BIGINT PRIMARY KEY,          -- 雪花ID
  tenant_id     BIGINT,                      -- 0=平台级通用模板，>0=企业自定义覆盖
  biz_type      VARCHAR(20),                 -- 营运类型：GENERAL普货 / DANGER危货 / PASSENGER客运
  level         TINYINT,                     -- 1=一级档案盒，2=二级归档子项
  sort_no       INT,                         -- 排序号（盒号一/二/三...）
  code          VARCHAR(50),                 -- 稳定编码（如 MONITOR_DAILY），业务模块引用用
  name          VARCHAR(100),                -- 档案盒/子项名称（逐字对齐政府目录）
  parent_id     BIGINT,                      -- 二级子项指向一级盒
  has_pdf       TINYINT DEFAULT 0,           -- 是否"本身就是一份可打印资料"
  renew_freq    VARCHAR(20),                 -- 更新频率：YEARLY一年一签/MONTHLY每月/QUARTERLY每季/ONCE入职一次性/ONCHANGE有变动时/DAILY每日/TRIP每趟/CERT按证照/LONG长期
  remark        VARCHAR(255),
  created_at    DATETIME,
  deleted       TINYINT DEFAULT 0
);
```

**说明**：
- `code` 是**稳定锚点**，业务模块用 `code` 绑定归档归属，不受名称/排序调整影响。
- `biz_type` + `tenant_id=0` 是平台预置模板；企业如需微调，复制为 `tenant_id=企业ID` 的覆盖版本。
- 一人一档/一车一档用 `level=1` 的特殊目录项，`parent_id` 为空，代码里特殊处理（按人/按车动态生成）。
- `renew_freq` 标注每个归档项的更新频率（见 2.1.1），预警引擎据此计算到期、服务商代录据此校验签字年份。

### 4.2 归档项表（业务成果物登记）

```sql
CREATE TABLE archive_item (
  id            BIGINT PRIMARY KEY,
  tenant_id     BIGINT,
  catalog_id    BIGINT,                      -- 归属的档案盒/子项（二级）
  data_type     TINYINT,                     -- 资料类别：1静态 2动态 3证件（见第二章）
  gen_mode      TINYINT DEFAULT 0,           -- 生成方式：1真实流程 2先台账后执行（仅动态资料有效）
  service_id    BIGINT,                      -- 方式二专用：关联增值服务单（计费/结算用）
  biz_module    VARCHAR(50),                 -- 来源模块：monitor/meeting/training/check...
  biz_id        BIGINT,                      -- 业务数据主键（如 meeting.id）
  title         VARCHAR(200),                -- 归档项标题（如"2026年10月安全生产月度会议"）
  occur_date    DATE,                        -- 归档项发生日期
  signed_year   SMALLINT,                    -- 签署年度（一年一签类用于自然年度到期判断）
  person_id     BIGINT,                      -- 一人一档专用：归属人员
  vehicle_id    BIGINT,                      -- 一车一档专用：归属车辆
  status        TINYINT,                     -- 0待生成 1已生成 2已打印 3已归档
  pdf_id        BIGINT,                      -- 关联成品PDF
  created_at    DATETIME,
  deleted       TINYINT DEFAULT 0
);
CREATE INDEX idx_archive_catalog ON archive_item(tenant_id, catalog_id);
CREATE INDEX idx_archive_biz ON archive_item(biz_module, biz_id);
CREATE INDEX idx_archive_type ON archive_item(tenant_id, data_type);
```

> `data_type` 字段把"三大类资料"落到数据层，归档全景页可按类别筛选、按类别差异化展示（证件类显示"到期倒计时"，动态类显示"最近一次执行时间"）。

## 六、PDF 生成引擎

### 5.1 技术选型

| 项 | 选型 | 理由 |
|----|------|------|
| 后端生成 | **JasperReports / 或 itext + 自定义模板** | Java 生态成熟，支持表格、图片、二维码 |
| 模板管理 | HTML → PDF（可选 Thymeleaf + Flying Saucer） | 版式灵活，前端可预览 |
| 二维码 | ZXing | 追溯：扫 PDF 上的码可定位到系统内源记录 |

**推荐方案**：**HTML 模板 + Flying Saucer（或 wkhtmltopdf）渲染 PDF**。理由：
- 模板用 HTML 写，产品/前端能直接调版式，效率高；
- 与"打印归档"的版式需求（页眉企业名、页脚页数、表格线）天然契合；
- 每个模板一个 HTML 文件，易维护、易新增。

### 5.2 统一版式规范（所有 PDF 遵循）

```
┌──────────────────────────────────────────────┐
│  页眉：企业全称 + 营运类型 + 档案盒编号/名称    │
│  标题：归档项名称（大字）                      │
│  ──────────────────────────────────────────── │
│  正文：表单/记录内容（表格化）                 │
│  ──────────────────────────────────────────── │
│  页脚：页码                                   │
└──────────────────────────────────────────────┘
```

**必备元素**：
1. 企业全称（与营业执照一致）
2. 档案盒编号 + 名称（对应政府目录）
3. 归档项名称 + 发生日期
4. 页码

### 5.3 模板清单（初期）

| 模板 code | 用途 | 数据来源 |
|-----------|------|---------|
| `TPL_TABLE_GENERIC` | 通用表格类（台账、清单） | 任意列表数据 |
| `TPL_MEETING` | 会议记录（含签到/照片/PPT页） | meeting 模块 |
| `TPL_TRAINING` | 培训记录（含签到/照片/考核） | training 模块 |
| `TPL_CHECK_THREE` | 一日三检记录 | check 模块 |
| `TPL_DANGER` | 隐患排查/整改（通知书+验收单） | danger 模块 |
| `TPL_ACCIDENT` | 事故档案（快报/汇总统计） | accident 模块 |
| `TPL_MONITOR` | 动态监控（违规登记/台账） | monitor 模块 |
| `TPL_CERT` | 证照归档页（证照 + 到期信息） | person_cert / vehicle_cert |
| `TPL_CONTRACT` | 责任书/承诺书（签字页） | person 模块 |
| `TPL_EMERGENCY` | 应急（预案/演练：方案+照片+签到） | emergency 模块 |
| `TPL_BUDGET` | 安全费用（营收证明/提取计划/使用台账） | budget 模块 |
| `TPL_RISK` | 风险辨识（手册/清单/告知卡/说明） | risk 模块 |
| `TPL_CREDIT` | 责任制考核（考核记录/结果） | credit 模块 |

> 模板随业务模块开发逐步补齐，初期先做通用表格模板 + 高频模板（会议/培训/三检）。

### 5.4 生成流程

```
业务数据保存
  → 自动登记 archive_item（带 catalog 归属）
  → 用户点击"生成PDF"（或批量生成）
  → 引擎取数据 + 匹配模板 → 渲染 PDF
  → 存 MinIO → 写 archive_pdf → 更新 item.status=已生成
  → 返回下载/预览
```

**异步化**：批量生成（如"一键生成整盒资料"）走异步队列，避免阻塞。

### 5.5 原型实现口径：下载 PDF / 打印 与「动态组织架构归档件」

> 生产环境按 5.1 走后端 HTML → PDF 渲染（Flying Saucer / wkhtmltopdf），成品存 MinIO 并写 `archive_pdf`；**原型阶段**为便于即时验收，采用「自包含 A4 横向 HTML + 浏览器打印」实现同一条链路，两者版式同源。

| 环节 | 原型实现 | 生产对应 |
|------|----------|----------|
| 版式 | `OrgChart.wrapDoc()` 把当前 PDF 预览页包成自包含 HTML：内嵌 `@page{size:A4 landscape;margin:12mm}`、页眉（企业全称）、页脚（归档年度 / 页码）、全部页面与架构图 CSS | 后端 HTML 模板 + `@page` |
| 下载 PDF | 「下载 PDF」按钮：① 下载 `归档项_年度_A4打印版.html`（离线可用）；② 打开打印窗口并自动唤起打印对话框，用户选「另存为 PDF」得到正式 PDF | 直接返回 `application/pdf` 文件流 |
| 打印 | 「打印」按钮只打开打印窗口（不重复下载）；`@media print` 隐藏工具条、去掉阴影、保留矢量连线与表格线 | 同版式后端渲染 |
| 预览 | PDF 弹窗内即为打印版正文，`所见即所归档` | 同版式后端渲染 |

**「安全管理组织架构」归档件（盒一 · 组织与任命类）**：

- 原先写死 `张伟 / 李强 / 王芳 / 陈刚` 的静态图已废弃，改为调用 `OrgChart.html({compact:true})`，正文由 `OrgData.posts()` 中**启用岗位**实时生成；岗位改名、换人、禁用、兼并、上提均实时反映到归档件（见 06 文档 5.1.2）。
- 页眉企业名统一取组织架构主数据 `OrgData.COMPANY()`，避免页眉与图内公司节点不一致。
- 归档频率为「有变动时更新」：组织架构变更（`rd_org_data_v2`）时，已打开的 PDF 预览自动重绘；点「重新生成」按当前范本与现有数据重渲染。
- 「安全生产责任制」归档件同理，正文取 `OrgData.activeDocPosts()`，禁用岗位自动剔除。

**「重新生成」通用规则**：每个「已生成 / 已打印」归档项均带「重新生成」按钮，按**当前应用范本 + 现有数据**重新渲染并打开预览；上传留存类（扫描件）提示重新上传，缺失类提示先生成或打印空白表手写补充。

## 七、"一一对应"的落地：归档全景页

### 6.1 页面定位

PC 端新增一个**「台账归档」**总览页，是整个归档能力的"中枢"：

- 左侧：按企业营运类型展示**档案盒目录树**（完全对齐政府目录）
- 右侧：选中某盒，展示该盒下的**归档项清单**，每项标状态（缺/待生成/已生成/已打印）
- 顶部：**"缺失项"提示**——哪些子项目前系统里还缺资料，用红色标出

### 6.2 状态与"缺项"提示

| 状态 | 含义 | 颜色 |
|------|------|------|
| 缺失 | 该归档项系统里还没有任何数据 | 红 |
| 待生成 | 有数据，但还没生成 PDF | 黄 |
| 已生成 | PDF 已生成 | 绿 |
| 已打印 | 用户标记已打印归档 | 蓝 |

> 归档全景页本质是**政府检查前的"自检清单"**：检查人员来之前，企业打开此页，红黄项一目了然，逐项补齐。

### 6.3 批量能力

归档项的批量操作分为**「批量生成」与「批量下载」**两类，二者职责不同：生成是把"待生成"项产出 PDF（可预览），下载是把已生成 / 已打印的 PDF 打包导出。

**批量生成（产出 PDF）**

- **一键批量生成（当前档案盒）**：对当前档案盒内所有"待生成"项一键生成 PDF，跳过"缺失 / 已生成 / 已打印"项；`src:'upload'` 上传留存类（证照、保单等）需人工上传、不可系统生成，自动跳过。
- **批量生成全部**：对所有档案盒的"待生成"项批量生成，规则同上。

**批量下载（导出 zip）**

- **单盒批量下载**：选中某档案盒 → 一键下载该盒所有已生成归档项的 PDF
- **全量下载**：一键下载全部档案盒 PDF（异步），打包 zip 按盒分目录
- **批量下载**：打包成 zip（按盒分目录）

> 两类操作均**按当前归档年度**生效（仅对所选年度实例操作），历史年度归档不受影响；与 §6.4.3 年度归档维度一致。

### 6.4 电子档案柜（通用模块）+ 服务商代录（专属能力）

> **核心拆分**：把「档案盒」做成**电子档案柜**通用模块，「一键下载整套台账 PDF」是**企业账号和服务商账号都具备的基础能力**；「代录台账」则是**服务商账号专属**的增值能力。两者不再混为一谈。

#### 6.4.1 电子档案柜（企业账号 + 服务商账号通用）

| 项 | 说明 |
|----|------|
| **定位** | 把 11 个档案盒做成「电子档案柜」，是归档中枢，对齐政府检查目录 |
| **可用角色** | `企业账号`（企业管理员/安全员等）与 `服务商账号` 均可进入 |
| **核心能力** | 选盒 → **一键下载该盒所有台账 PDF**（含全量下载、打包 zip） |
| **状态管理** | 每个归档项标状态（缺失/待生成/已生成/已打印），红黄绿一目了然，作为政府检查前的自检清单 |

**点击文件名即预览（无独立预览按钮）**：归档项名称（及已上传文件的文件名 chip）均可点击**直接预览 / 触发对应操作**，不再单列「预览 PDF」按钮——已生成 / 已打印→打开 PDF；待生成→弹出生成框；上传来源→弹出上传框；已上传文件→预览已上传件。与盒内文件夹分组、上传留存、年度归档完全兼容。

**盒内文件夹分组（与范本管理一致）**：每个档案盒内归档项按业务语义**分组折叠**展示——分组头 = 图标 + 组名 + 数量 + 折叠箭头，组内带序号，点击分组头可展开 / 收起。例如盒一 = 证照类 / 组织与任命类 / 责任与承诺类 / 计划与保险类；盒二 = 法律法规清单 / 管理制度（24 项 `YT-ZD01`~`YT-ZD24`）/ 制度目录。

**与范本管理同源**：盒二 24 项制度 + 目录与「范本管理」共用 `assets/archive_shared.js` 数据源（`buildBox2Institutions()` 由 `SYS_DOCS` 生成），编号、名称、PDF 正文**一一对应**；任一页面修改制度，另一页面同步可见。

#### 6.4.2 服务商代录（服务商账号专属）

> **定位**：面向不会使用线上平台的小微普货客户，由**服务商账号**代操作，**无需推送给企业**，通过「上传照片 + 复用历史签字 + 调用范本库」直接生成台账。本质是方式二"先台账后执行"在**批量补齐场景**下的产品化封装，做到**最简化流程、最高效率**——企业全程零参与，仅签字数据缺失时才需配合。

| 项 | 说明 |
|----|------|
| **操作角色** | `服务商账号`（见 01 文档 3.2）。普通客户账号、企业管理员均无此入口 |
| **适用客户** | 小微普货企业（车辆少、无专职安全员、难用线上平台） |
| **典型场景** | 服务商已帮客户收集了 1-10 月培训照片、会议照片、隐患排查照片；系统自动读取企业历史签字数据复用，缺失签字才发起企业线上签字，随后调用范本生成对应台账 PDF 打印归档 |
| **范本调用** | **必选**——从范本库（见 09 文档）选择范本，系统把照片、签字数据填入范本生成台账 |

**四步向导流程**（独立「服务商代录工作台」）：

1. **选择客户** —— 在服务商账号名下服务的企业中选目标客户（标注"有历史台账待补/新客户"）。
2. **选盒 + 批量上传照片** —— 勾选要代录的档案盒；按「照片类型（培训/会议/隐患排查/应急演练/一日三检）× 月份」批量上传，系统自动补齐对应月份的台账材料，缺项月份红色标出。
3. **签字数据匹配**（**唯一企业触点**）—— 系统自动读取该企业的**历史签字库**（企业日常留痕、历史代录、人车档案中的签字数据），对每个岗位人员做三态判定：
   - **✅ 已复用历史签字**：该人员有可用历史签字 → 自动复用，无需任何操作；
   - **⏳ 待企业线上签字**：无历史签字 → 服务商发起签字请求，企业人员登录企业账号配合签字后回填；
   - **🖨️ 打印手签（兜底）**：企业无法线上签 → 生成带签字栏 PDF，线下补签后归档。
4. **选范本生成** —— 从**范本库**（按所选档案盒过滤，含责任书/承诺书/告知书/任命书/制度/预案/台账等）勾选范本，一键生成对应台账 PDF。

> **关键原则**：签字环节是代录全流程中**唯一需要企业参与**的环节，且仅在「历史签字数据缺失」时触发。有历史签字数据的客户（如已签约服务过一段时间的客户），整个代录流程企业零参与、纯服务商操作。

**与电子档案柜的关系**：电子档案柜是**通用入口**（谁都能进、都能下载已有台账），服务商代录工作台是**服务商专属入口**（生成"还没有的"台账）。代录生成的台账会**回写**到对应企业的电子档案柜，企业账号随后也能看到并下载。每次代录形成一条**服务单**（为哪家企业、补了哪些台账、耗时、是否收费），便于运营方结算对账。

#### 6.4.3 年度归档维度（按自然年度切换查看）

> **新能力**：整体档案**按自然年度归档**，顶部「归档年度」切换条可在不同年度间切换，查看该年度的归档状态。档案盒目录、归档项列表、顶部汇总（缺失/待生成/已生成/已打印）、到期重签预警横幅均**随所选年度联动**；各年度状态**相互隔离**，在当前年生成/上传/标记打印仅作用于当前年，历史年归档不受影响。

| 项 | 说明 |
|----|------|
| **年度切换条** | 顶部「归档年度」随真实时间默认当前年；**最近 3 个年度（前年 / 去年 / 当前年）平铺显示**，当前年带"今"角标；**超过 3 年的更早年份折叠进「更多历年 ▾」下拉**（展开可选中，选中后自动收起）；当前年标注"逐年重做/重签"，历史年标注"已沉淀的台账" |
| **数据结构** | 每个归档项在各年度有独立状态：原单年度字段（`st`/`file`/`signedYear`）派生为按年映射 `y[年度]`，读取时统一走 `Y(item)` 取当前年状态 |
| **历史年度语义** | 历史年度的归档项视为**已沉淀归档**——原"缺失/待生成"在历史归档中自动计为当年已完成（已生成/已打印），体现多年台账的延续性 |
| **当前年度语义** | 当前年**逐年重做/重签**：一年一签类（责任书/承诺书/禁毒承诺书等）若签署年早于当前年 → 自动转为"待生成"（需重签）；其余沿用初始状态 |
| **状态隔离** | 在 2026 年生成某台账、在 2025 年标记已打印，两个年度的状态互不污染（验证：2026 责任书生成后切回 2025 仍为"已打印"） |
| **PDF 落款** | 每份 PDF 的页眉 / 页脚均标注「归档年度：xxxx」，打印装盒时直接区分年度卷宗 |
| **兼容能力** | 与盒内文件夹分组、每项"上传/生成/预览"、服务商代录回写等能力完全兼容，年度切换不破坏既有交互 |

**配套联动**：重签预警横幅（一年一签项跨年需重签）改为按**当前归档年度**判断——切到历史年不提示，切到当前年提示该年待重签项，与"年度归档"语义自洽。

#### 6.4.4 上传留存能力（每项独立上传入口）

> **定位**：对应 §2.1 中"②' 上传留存资料"与"③ 证件资料"的生产方式——凡是**企业自备 / 外部平台产出 / 证照类**归档项，系统不生成正文，而是由企业**上传实物扫描件 / 外部平台导出文件**留存到电子档案柜。每个归档项都具备独立的上传入口，做到"能生成的生成、该上传的上传"。

| 项 | 说明 |
|----|------|
| **上传来源项（主操作 = 上传）** | `src:'upload'` 类归档项（营业执照、经营许可证、保险单、罐体检测证明、专用标识喷涂证明、职业健康检查报告等证件 / 实物类）：主按钮即"上传"，上传后即视为该归档项"已留存"（`st`→已生成） |
| **生成类项的"上传留存"** | 系统生成 / 打印手写类项（责任书、会议记录、培训台账等）额外带一个 outline"上传"按钮，用于**上传该台账的纸质签字页 / 现场照片扫描件**作为留存佐证，与生成的 PDF 并存 |
| **上传弹窗** | 点击上传 → 弹出 `uploadModal`：拖拽 / 选择文件区 + 确认按钮；未选文件时兜底命名为 `xxx_扫描件_日期.pdf` |
| **留存落地** | `doUpload()` 将文件名写入 `archive_item.file`（并落一条 `archive_pdf`，`gen_mode='upload'`），状态置"已生成"，实时重渲列表与档案盒目录红黄绿点、顶部汇总 |
| **文件 chip + 直接预览** | 已上传项显示文件名 chip（带"已上传留存"标识），**点击文件名或 chip 可直接预览**已上传文件，无需独立按钮 |
| **与年度维度兼容** | 上传作用于**当前归档年度**的该实例，不影响历史年归档；切年度后上传入口与状态随当前年呈现 |

**数据模型映射**：上传留存对应 `archive_item.src='upload'`（资料来源 = 企业自备 / 外部导入），证件类 `data_type=3`；上传的文件作为一条 `archive_pdf` 记录（`file_path` 存 MinIO/OSS，`gen_time` 记上传时间，`template_code` 可为空），通过 `item.pdf_id` 关联。与 §五 4.3 的 PDF 成品表一致。

#### 6.4.5 一键批量生成（勾选式生成能力）

> **定位**：与 §6.3 一致——「批量生成」负责把"待生成"归档项**产出 PDF**（状态流转 `wait → done`，文件名记为 `xxx_归属年度.pdf`），与「批量下载」的"打包导出"职责分离。面向运营人员"一次性把整盒 / 全部台账生成齐"的高频场景。**支持三级勾选**：目录勾选整个档案盒、盒内勾选某个分组、或逐条勾选，按需生成。

| 项 | 说明 |
|----|------|
| **目录级勾选（整盒）** | 左侧「档案盒目录」每个盒项左侧新增勾选框（`toggleTreeBox`）：一键勾选 / 取消**该盒全部项**；盒项部分勾选时显示**半选态**。目录顶部另设「全选全部档案盒」（`toggleTreeAll`）：勾选 / 取消所有盒所有项 |
| **分组级勾选（分组）** | 盒内每个分组标题左侧新增勾选框（`toggleGroup`）：勾选即选中**该分组内全部项**；部分勾选时显示**半选态** |
| **行级勾选（单条）** | 每个归档项行首勾选框（`toggleSel`）；勾选状态统一由 `selSet`（`盒序号_项序号` 集合）维护，跨盒切换保留 |
| **全选本盒** | 盒详情头部「全选本盒」勾选框（`toggleBoxAll`）：一键勾选 / 取消当前盒全部项；部分勾选时显示**半选态**。三级勾选任一变动都经 `updateSelAllState()` 同步盒头部、分组、目录当前盒、全选全部的勾选 / 半选态 |
| **一键批量生成（全勾选项 · 可跨盒）** | 顶部工具栏按钮 `batchGen()`：遍历**所有档案盒**已勾选且 `st='wait'` 的项生成（目录 / 分组 / 单条任意组合的勾选都可跨盒生效），未勾选项不动 |
| **批量生成全部（全部盒 · 全部待生成）** | 顶部工具栏按钮 `batchGenAll()`：对所有档案盒的 `st='wait'` 项批量生成（不依赖勾选，作为"全量补齐"快捷入口） |
| **跳过上传留存类** | `src='upload'` 项（证照 / 保单 / 外部平台导出文件）需人工上传，系统不伪造正文，**自动跳过、保留为待上传** |
| **空选 / 全不可生成提示** | 未勾选任何项 → toast「请先勾选要生成的归档项」；勾选项均为上传类 / 已生成 / 缺失 → toast「勾选项均不可生成（上传类需人工上传 / 已生成 / 缺失）」 |
| **按当前归档年度生效** | 仅对所选"归档年度"实例操作：历史年度已沉淀归档，不参与生成；切到历史年点批量生成会提示"已无待生成项" |
| **落库与联动** | 生成即写入 `archive_item.st='done'` + `file`，实时重渲盒目录红黄绿点、盒内列表、顶部汇总、重签预警横幅；生成后自动清除这些项的勾选 |

**数据模型映射**：批量生成的产物即一条 `archive_pdf`（`gen_mode=1` 真实流程 / `2` 先台账后执行，按各归档项原始生成方式而定，`gen_year` 记归属年度），与 §五 4.3 PDF 成品表及 §6.4.3 年度归档维度一致。

## 八、业务模块接入规范（贯穿全程的约束）

> 这一节是给"后续所有业务模块详细设计"的**强制约束**——每个业务模块在设计时，必须回答"我的成果物落在哪个档案盒"。

### 7.1 每个业务模块的必答清单

| 必答项 | 说明 |
|--------|------|
| 归属档案盒 code | 本模块数据属于哪个档案盒（如 `MONITOR`） |
| 归档项类型 | 产生哪些具体归档项（如"每日台账""月报""违规教育"） |
| 归档粒度 | 按天？按次？按人？按车？ |
| PDF 模板 | 用哪个模板（或需新增模板） |
| 触发时机 | 什么时候登记归档项（保存即登记/审核通过后/手动） |
| **生成方式支持** | 本模块是否支持"先台账后执行"（方式二）？由谁操作？ |

### 7.1.1 服务商账号与"录入生成台账"权限（方式二的入口）

> 方式二"先台账后执行"是**运营方提供的增值服务**。服务商账号（见 01 文档 3.2 / 00 文档 4.5.1）**拥有修改所有台账记录的权限，可通过录入直接生成对应台账**——这是方式二的能力基础，也是服务商账号的众多功能之一（其核心是管理系统所有模板、视频库、题库等配置）。

| 项 | 说明 |
|----|------|
| 角色 | `服务商账号`（平台侧服务商/渠道商账号，由平台超管创建，服务名下企业；见 01 文档 3.2） |
| 台账权限 | **修改所有台账记录 + 录入即生成台账**（跨企业，作用于名下服务的企业） |
| 与客户账号区别 | 客户只能走方式一（真实流程）；服务商账号可录入生成台账（方式二） |
| 操作留痕 | 录入/修改操作全量记录（谁、何时、为哪个企业、改了什么），不可篡改 |
| 边界 | 服务商账号只能"录入生成台账"，不能代企业做真实动作（三检/培训的实际执行仍是客户线下完成） |

> 该角色的完整权限模型在《01-SSO统一认证与组织权限》中定义，本文档只约定"方式二的入口权限归属于服务商账号的录入生成能力之一"。**代录/录入生成是服务商账号的一个功能，不是服务商账号的定义。**



### 7.2 各模块 → 档案盒映射总表（核心）

| 业务模块 | 归属档案盒（普货/危货通用） | 归档粒度 | 关键归档项 |
|----------|---------------------------|---------|-----------|
| 企业信息管理 | 一、公司档案及管理层档案 | 单份 | 营业执照、道路运输经营许可证、安全组织架构、二级维护计划、责任险 |
| 组织架构 | 一、公司档案及管理层档案 | 单份 | 安全组织架构、成立领导小组通知、人员任命书 |
| 人员管理 | 一 + 一人一档 | 按人 | 管理人员档案、责任书、承诺书、岗位危害告知书、考核证明 |
| 车辆管理 | 一车一档 | 按车 | 车辆信息登记表、行驶证、营运证、保险、技术档案 |
| 制度档案 | 二、安全生产管理制度及操作规程 | 单份 | 法律法规目录清单、制度汇编（含操作规程） |

| 考核奖惩 | 十一、一人一档/一车一档 | 按月/按次 | 从业人员考核记录（考核事项/内容/标准/评分）、从业人员奖惩公示（考核类型/周期/结果/奖惩详情） |
| 诚信考核 | 十一、一人一档/一车一档 | 按月 | 从业人员考核记录（责任制考核评分，随结果沉淀一人一档诚信/违章/奖惩） |
| 安全投入 | 五、安全生产费用提取与使用 | 按月 | 营收证明、提取标准计划、使用台账（发票/收据） |
| 动态监控 | 六、动态监控及交通违法管理 | 按天 | 每日台账、故障异常、在线率、月报、违规教育 |

| 应急管理 | 八（危货）/ 七（普货） | 按次 | 应急预案、备案回执、演练、培训、器材 |

| 一日三检 | 十（危货）/ 九（普货） | 按月汇总 | 三检月报汇总表（单车单日明细由监管现查现打，不装盒） |

> **注意**：普货和危货的盒号不同（因为危货多了"停车场管理"导致顺延），但**归档项归属的 `code` 是稳定不变的**，盒号只是展示层。业务模块绑 `code`，不绑盒号。
