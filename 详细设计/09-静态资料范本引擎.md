# 静态资料范本引擎（详细设计）

> 版本：v1.0（初稿，基于盒一范本实测）
> 日期：2026-10-27
> 状态：待与用户对齐关键设计点
> 依赖：《08-台账归档与PDF生成引擎.md》的三大类资料分类

---

## 一、定位与目标

静态资料（①）是三大类资料中的**"生成器"**类：制度、预案、责任书、承诺书、任命书等范本类资料。

**核心目标**：客户填一次关键信息（企业信息、人员、岗位），系统就能从范本库**自动生成**全套静态台账 PDF，无需客户逐份手工编辑 Word。

**本质**：把"原始 Word 范本"改造成"带变量占位符的系统范本"，运行时用客户数据填充变量，生成可打印 PDF。

## 二、盒一范本实测结论（已解析 25 份文件）

| 组织架构图 | 1 | 安全组织架构图（WPS .doc） | — |

**合计 27 份文件（含 1 张图片）**，其中 4 类按岗位拆分（共 23 份）。

### 2.2 关键结构特征（决定引擎设计）

1. **范本主体是固定条款文字**：责任书的安全职责、告知书的岗位危害、承诺书的承诺内容等，每个企业几乎一样，是"死"文字。
2. **变量极少且集中在文首/文末**：
   - 企业全称（如"佛山市优成得物流有限公司"）
   - 人员姓名（如"马志勇"）
   - 岗位名称（主要负责人/安全员/监控员/驾驶员/行政财务）
   - 日期（签订日期、生效日期、告知日期）
   - 年度（如"2025年年度"）
3. **范本按岗位物理拆分**：同一类责任书有 6 个独立文件，而非一个文件里做下拉选择。这是**改造时必须决策的点**（见 4.2）。

### 2.3 普货 vs 危货 差异（本次要区分）

用户要求"普货和危货要做区分，先做普货"。盒一是普货版。已确认的差异点在《08》文档 2.4 已列：

| 差异点 | 普货 | 危货 |
|--------|------|------|
| 一人一档 | 无禁毒承诺书 | 多"禁毒承诺书" |
| 责任书/承诺书范围 | 普货岗位 | 危货多押运员、装卸管理员、车辆技术管理员等岗位 |

> **已确认（危货范本已单独提供）**：危货版范本由用户**单独提供**（《危货制度范本.zip》21 文件），独立于普货（23 文件），不是"同一批范本按岗位补全"。详细对比见《样例/盒二制度范本对比分析-v2.md》——普货 13 项共有 + 10 项独有，危货 13 项共有 + 8 项独有，岗位数不同（普货 10 岗 / 危货 12 岗）。

## 三、变量字段字典（范本引擎的核心）

### 3.1 字段字典设计原则

**范本引擎的本质 = 字段字典 + 范本模板 + 填充器**。字段字典是"系统里有哪些可填充的变量"，是范本与客户数据之间的桥梁。

### 3.2 字段分类（三级）

| 分类 | 说明 | 数据来源 | 示例 |
|------|------|---------|------|
| **企业级字段** | 全企业通用，填一次 | 企业信息管理模块 | 企业全称、法人、地址、电话、经济类型 |
| **人员级字段** | 随人变化 | 人员档案模块 | 姓名、身份证号、岗位、联系电话 |
| **上下文字段** | 每次生成时确定 | 生成时传入 | 签订日期、年度、生效日期 |

### 3.3 字段字典初稿（基于盒一范本提取）

### 3.3.1 新增范本的变量说明（成立通知 / 复工复产）

**① 关于成立安全生产领导小组的通知**（单范本，变量少）：
- 固定条款：领导小组职责（11 条，全部企业一致，写死在范本）
- 变量：`company_name`、`doc_no`（文号，可留空手填）、`leader_name`/`deputy_names`/`member_names`（组长/副组长/成员，从 06 领导机构自动读取）、`sign_date`
- 说明：成员列表用列表变量渲染，多人逗号分隔或逐行列出

**② 复工复产方案（"六个一"套装，1 套含 7 个文件）**：
- 套装组成：① 安全生产诚信承诺书 ② 一次领导班子安全生产专题会议 ③ 一份节后复工复产方案 ④ 一次全体员工大会 ⑤ 一次全体员工安全培训教育 ⑥ 一份应急方案 ⑦ 一次节后复产安全检查记录表
- 变量：`company_name`、`leader_name`/`deputy_names`/`member_names`（复工领导小组）、培训时间/地点（留空手填）、`sign_date`
- 说明：这是一套**联动生成**的范本（一次生成 7 份），企业内部人员姓名、公司名自动填充，培训/检查的具体内容留空手填

**③ 任命书 / 制度（线下台账比对新增字段）**：
- 任命书：文件头（`company_name` + `doc_no` 文件编号）+ 正文（`person_name` + 岗位/专兼职）+ `start_date` 生效日期 + 盖章。区分"专职安全生产管理人员"与"兼职监控人员"两种任命表述（`{% if %}` 条件段）。
- 制度：文件头（`doc_no` 文件编号 + `start_date` 实施日期 + `issuer` 签发人）+ 制度正文 + 盖章。
- 变量：`doc_no`、`start_date`、`issuer`、`person_name`、岗位（专兼职标志）
- 说明：`doc_no` 与成立通知共用文档编号池（企业简称 + 文种 + 年度 + 序号）。线下任命书文件编号如 `0-17780`、制度编号如 `ZD13`——系统统一由编号池自动生成，可改。

### 3.4 字段填充策略（核心规则，全局适用）

> **"系统有的自动填，没有的留空手填。"** —— 所有范本统一遵循。

1. 变量对应系统已采集字段（企业信息/人员/岗位）→ **自动填充**
2. 变量对应系统未采集字段 → **留空**，生成 PDF 时显示空栏，客户打印后手填
3. 字段缺失**不阻断生成**——渲染引擎遇到取不到值的变量，渲染为**空下划线/空栏**，而非报错

> 对齐《00》架构文档 4.0"先让系统能用，再让资料完整"的总原则。运输从业人员少打字，手填为主，系统填充是"能省则省"的辅助。

### 3.5 变量类型（需支持的三种）

| 类型 | 说明 | 示例 |
|------|------|------|
| **标量变量** | 单个值 | `{{company_name}}`、`{{person_name}}` |
| **条件段落** | 按条件显示/隐藏 | `{% if post == '驾驶员' %}` |
| **列表变量** | 结构化条目数组（循环渲染） | `{{hazard_list}}`（危害项名称+描述） |

> 告知书的"岗位危害清单"就是列表变量，范本引擎需支持列表型变量的循环渲染。

## 四、范本化改造方案（核心决策点）

### 4.1 原始范本 → 系统范本 的改造流程

```
原始 Word（固定文字 + 人工改）
        ↓ ① 文本结构化
提取出固定条款 + 识别变量位置
        ↓ ② 变量占位 + 条件段落
把"企业名/人名/岗位/日期"替换为 {{变量key}}
岗位职责差异用 {% if post == 'xx' %} 条件段落
        ↓ ③ 转为 HTML 范本
范本内容存为 HTML（含 CSS 版式 + 变量占位 + 条件段落）
        ↓ ④ 存为系统范本
范本入库（含元数据：名称、类型、档案盒归属、岗位范围、普货/危货）
        ↓ 运行时
客户填字段 → 引擎填充变量 + 解析条件 → 渲染 HTML → 生成 PDF
```

### 4.2 范本内容形态（已拍板：HTML）

范本内容统一存 **HTML（含 CSS 版式）**，理由：

| 维度 | HTML 优势 |
|------|----------|
| 版式调整 | 改 CSS 即改字体/字号/行距/页边距/签字栏位置，无需碰每个范本 |
| PDF 衔接 | 与《08》PDF 引擎"HTML → PDF"方案零转换 |
| 条件段落 | 模板语法（`{% if %}`）在 HTML 里最自然 |
| 电子签定位 | 签字栏、日期栏用 HTML 精确定位，电子签图片直接嵌入 |

> 原始 Word 仅作为"改造源材料"，改造后一律存 HTML，不再保留 Word 副本作为运行时依赖。

### 4.3 关键决策：按岗位拆分 vs 单范本多岗位（已拍板：分层）

**已确认：方案 B'（分层）——结构相同才合并，整段替换就独立。**

经过对盒一 6 份责任书、5 份任命书、6 份承诺书的实测对比，发现岗位间的差异有两种截然不同的形态，不能一刀切：

| 差异形态 | 特征 | 做法 | 适用范本 |
|---------|------|------|---------|
| **增减型** | 条款结构一致，仅岗位名/人名不同，或部分段落增减 | 单范本 + `{{变量}}` + `{% if %}` 条件段 | 任命书、岗位告知书 |
| **替换型** | 整段条款不同 + 签订关系/签字结构变化 | **保留按岗位独立范本** | 责任书、承诺书 |

**判断标准（唯一一条）**：岗位间差异是"**增减**"还是"**替换**"。

- 增减 → 合并为单范本（岗位做变量 + 条件段）
- 替换 → 独立范本

> **实测结论**（详见 `样例/责任书-改造结论.md`）：责任书的 6 个岗位，标题不同（目标责任书 vs 责任书）、签订关系不同（单边盖章 vs 双边签字）、职责整段不同（14/16/10/21/12 条）——是"替换型"，应保留独立范本。而任命书 5 岗位几乎只差人名和岗位名——是"增减型"，适合合并为单范本。

**条件段落语法示例**（仅用于"增减型"范本）：

```html
<p>{{company_name}}与{{person_name}}签订安全生产责任书</p>

{% if post == '主要负责人' %}
  <p>（主要负责人专属职责条款...）</p>
{% endif %}

{% if post == '驾驶员' %}
  <p>（驾驶员专属职责条款...）</p>
{% endif %}
```

**方案 B' 的优势落地**：
- "增减型"范本从"每岗位一份"收敛为"每类一份"，管理成本骤降
- "替换型"范本保留独立，避免单个范本文件塞多套整段内容而变得臃肿难维护
- 字段字典统一管理岗位枚举，范本引用岗位变量即可
- 新增岗位时：增减型加 `{% if %}` 段，替换型新建独立范本

### 4.4 岗位字典（需对齐组织架构）

岗位是范本的核心变量。需与《06-组织架构.md》的岗位体系对齐：

| 岗位 | 普货 | 危货 | 是否需任命书 | 说明 |
|------|------|------|------------|------|
| 主要负责人 | ✅ | ✅ | ✅ | 法规强制 |
| 安全员 | ✅ | ✅ | ✅ | 法规强制 |
| 监控员 | ✅ | ✅ | ✅ | 危货需专职/兼职 |
| 行政/财务 | ✅ | ✅ | ✅ | 盒一范本有 |
| 押运员 | — | ✅ | ❌ **不需要** | 一线从业人员 |
| 装卸管理员 | — | ✅ | ✅ | 管理岗（需持证） |
| 车辆技术管理员 | — | ✅ | ✅ | 管理岗 |
| 停车场管理员 | — | ✅ | ✅ | 管理岗 |
| 调度员 | — | ✅ | ✅ | 管理岗 |
| 驾驶员 | ✅ | ✅ | ❌ **不需要** | 一线从业人员 |

> **任命书适用范围（已确认）**：只针对**管理岗位**。驾驶员、押运员是**一线从业人员，不需要任命书**（他们凭劳动合同、从业资格证即可）。
>
> 范本生成时，根据企业营运类型 + 已配置岗位，**只生成该企业实际有人的岗位范本**，不生成空岗位。

## 五、岗位内容库（内容外置，已确认）

### 5.1 为什么内容要外置

> 用户反馈第 7 条：不同岗位的**责任目标、职责、岗位危害**等内容，要和组织架构的**岗位描述**关联，支持用户编辑，编辑后自动更新范本。

**核心设计：范本不写死岗位内容，而是"引用岗位内容库"。**

```
范本模板（HTML，只有骨架 + 引用占位）
    ↓ 引用
岗位内容库（岗位描述：职责/目标/危害，可按岗位编辑）
    ↓ 数据来源
组织架构模块的岗位配置
```

**好处**：
- 用户改一次岗位职责，所有引用该岗位的范本（责任书、告知书、承诺书...）**同时更新**
- 不用在每份范本里重复维护同样的职责文字
- 岗位内容成为"组织架构"的一部分，天然统一

### 5.2 岗位内容库结构

每个岗位可维护以下内容块（对应范本里的片段）：

| 内容块 code | 含义 | 用于范本 |
|------------|------|---------|
| `duty` | 安全职责（条目列表） | 责任书 |
| `target` | 安全目标（条目列表） | 责任书 |
| `hazard` | 岗位危害（名称+描述的条目列表） | 岗位告知书 |
| `prevent` | 防护措施（条目列表） | 岗位告知书 |
| `commitment` | 承诺条款（条目列表） | 承诺书 |
| `post_desc` | 岗位描述（一句话） | 任命书 |

> 范本里引用方式是"占位 + 内容块 code"，如 `{{duty:安全员}}` 表示"取安全员岗位的职责列表"。渲染时从岗位内容库取。

### 5.3 编辑与更新

- **企业可编辑**：企业在"组织架构 - 岗位管理"里可改本企业岗位的职责/目标/危害内容
- **改后即生效**：改了岗位内容，下次生成范本自动用新内容（已生成的旧 PDF 不变，保持历史快照）
- **与组织架构的关系**：岗位内容库挂在组织架构的岗位下，是岗位的属性

## 七、范本三层架构与分组管理（已确认）

### 7.1 三层范本体系

```
第一层：系统级范本组（超管维护，按运输形态分组）
    ↓ 创建企业时分配范本组
第二层：企业范本（继承系统级，可个性化修改）
    ↓ 生成时使用
第三层：企业实际生成的台账 PDF
```

| 层 | 谁维护 | 可改什么 |
|----|--------|---------|
| **系统级范本组** | 服务商账号（见 01 文档 3.2） | 范本内容、分组、岗位内容默认值 |
| **企业范本** | 企业管理员 | 在系统级基础上改本企业个性化版本 |
| **生成的台账** | 系统 | 按企业范本 + 企业数据生成 PDF |

### 7.2 车辆类型清单（用户确认）

企业**首次接入时就勾选涉及的车辆类型**，后续制度/规程按勾选定制。

**普货（14 种）**：

（注：用户提供的 7 大类中还含**栏板车、牵引车、自卸车**，一并纳入类型字典）

**危货（16 种）**：
罐车、厢车、集装箱、气瓶运输车、爆破器材运输车、冷藏车、腐蚀性物品运输车、放射性物品运输车、固体危险货物运输车、危险废物运输车、易燃液体运输车、液化气体运输车、剧毒化学品运输车、爆炸品运输车、压缩气体运输车、低温液体运输车

### 7.3 制度生成原则（核心，用户确认）

| 类型 | 制度结构 |
|------|---------|
| **普货** | 1 套通用安全管理制度 + 按车辆作业特点设**专项操作规程** |
| **危货** | 1 套通用安全管理制度 + **两层结构**专项规程（车辆结构 × 作业环节/岗位） |
| **特殊业务** | 通过**附件**补充，不重做整套制度 |
| **应急预案** | **按车辆类型**一套（通用版骨架 + 车型专项处置方案） |

**关键原则**：
1. **普货可较大程度通用**——按作业特点归为 7 个制度大类，同类车型共用一套规程
2. **危货不能完全照搬普货分类逻辑**——采用**两层结构**：车辆结构 × 作业环节/岗位（危险货物类别降级为条件性附加条款）
3. **制度最终需结合企业实际承运的危险货物类别及适用法规审核**
4. **新增车型只判断是否涉及新风险/新操作要求**，无须重编整套制度
5. **应急预案纳入"制度生成"联动**——生成制度时一并生成应急预案（危货除外，见 7.9）

### 7.3.1 区域维度（用户确认：全区域通用 + 个别区域特殊版）

> 大部分客户使用**全区域通用版**。个别区域监管**只认本区域特殊版本**时，才需按该区域的特殊版生成。

| 场景 | 范本 |
|------|------|
| 默认 | 全区域通用版（普货一套 / 危货一套） |
| 个别区域有特殊监管要求 | 挂载**区域特殊版**（如"乐从版"） |

**设计**：范本组增加**区域维度**（`region` 字段），默认 `ALL`（全区域通用）。当某区域监管要求特殊时，超管为该区域建立 `region=特定区域` 的特殊范本组；企业落在该区域时，优先用区域特殊版，否则回落通用版。区域差异本质仍是"变量 + 个别条款"，不破坏三层范本架构。

### 7.4 多维范本分组模型（已确认，v2 修正）

> 决策：普货按"作业特点归大类"，危货按"**车辆结构 × 作业环节/岗位**"两层结构。

```
企业勾选车辆类型（多选）+ 危货另选承运货物类别
    ↓ 系统映射
① 通用制度层（所有企业共用）
    └─ 1 套通用安全管理制度（不因车型变化）
    ↓
② 专项规程层（按勾选拼装）
    ├─ 普货：7 个制度大类
    │    1 厢式及封闭类（厢车/飞翼车）
    │    2 栏板及仓栅类（高栏车/仓栅车/栏板车）
    │    3 集装箱及牵引类（集装箱车/牵引车）
    │    4 自卸及工程类（泥头车/自卸车）
    │    5 罐体及散装物料类（液体罐车/粉粒物料车）
    │    6 平板及大件类（平板车/低平板车/大件运输车）
    │    7 专项功能类（冷藏车/随车吊等）
    └─ 危货：两层结构（v2 修正）
         第一层·车辆结构：罐式 / 厢式包装 / 集装箱 / 气瓶
         第二层·作业环节/岗位：驾驶 / 押运 / 装卸管理 / 危险货物运输 / 动态监控
                 / 组织调度 / 防护用品穿戴 / 罐体清洗消毒 / 各级维护 / 安全检查检测
         → 两层交叉装配专项规程
         → 危险货物类别（易燃/腐蚀/毒害/爆炸/放射性）降级为「条件性附加条款」，
            不再独立成层（如"运输易燃易爆品应 X 时前完成""酸碱接触岗位戴面罩"）
    ↓
③ 附件层（特殊业务补充）
    └─ 不重做制度，用附件补充特殊要求
```

### 7.5 普货制度大类（7 类，用户确认定稿）

> 普货可较大程度通用：**14 种车型 → 收敛为 7 个制度大类**。

| # | 制度大类 | 覆盖车型 |
|---|---------|---------|
| 1 | **厢式及封闭运输类** | 厢车、飞翼车 |
| 2 | **栏板及仓栅运输类** | 高栏车、仓栅车、栏板车 |
| 3 | **集装箱及牵引运输类** | 集装箱车、牵引车 |
| 4 | **自卸及工程运输类** | 泥头车、自卸车 |
| 5 | **罐体及散装物料运输类** | 液体罐车、粉粒物料运输车 |
| 6 | **平板及大件运输类** | 平板车、低平板车、大件运输车 |
| 7 | **专项功能运输类** | 冷藏车、随车吊等 |

> 新增车型只需判断归入已有大类，或新增一个大类；**无须重新编制整套制度**。

### 7.6 危货两层结构（用户确认定稿，v2 修正）

> 危货**不能完全照搬普货的分类逻辑**，采用**两层结构**：

**第一层：车辆结构**

罐式、厢式包装、集装箱、气瓶（按车身结构划分专项规程）

**第二层：作业环节/岗位**

驾驶、押运、装卸管理、危险货物运输、动态监控、组织调度、防护用品穿戴、罐体清洗消毒、各级维护、安全检查检测（共 10 类，对应危货操作规程范本的 10 个章节）。

> **v2 修正说明**：原定义第二层为"危险货物类别（易燃/腐蚀/毒害/爆炸/放射性）"。经危货范本实测，危险货物类别在范本中**并不独立成篇**，而是以"运输特定类别危险货物时，还应检查相关附加装备"这类**条件性条款**散落在操作规程里。因此修正为：

```
企业勾选：车身结构（第一层） + 岗位/作业环节（第二层，通常全量）
    ↓ 交叉装配
危货制度包 = 通用制度
           + 第一层：车辆结构专项规程（罐式/厢式包装/集装箱/气瓶...）
           + 第二层：作业环节专项规程（驾驶/押运/装卸/监控/清洗/维护/检测...）
           + 条件性附加条款（危险货物类别：易燃/腐蚀/毒害/爆炸/放射性...）
```

**交叉生成示例**：
- 勾选"罐式 + 易燃液体" → 罐式专项规程 + 全量作业环节规程 + 易燃液体附加条款
- 勾选"厢式包装 + 腐蚀性物质" → 厢式包装规程 + 全量作业环节规程 + 腐蚀性附加条款

> **为什么危险货物类别降级为条件条款**：实际危货范本中，货物类别的差异不是"整篇规程不同"，而是"多几条注意事项"（如易燃易爆品限时运输、酸碱岗位戴面罩、特定类别查附加装备）。独立成层会导致规程数量爆炸（4 结构 × 5 类别 = 20 套），而实际只需 4 套结构规程 + 几条条件条款。

### 7.6.1 危货专项台账范本（动态台账表头，归入现有盒）

> 用户确认：危货专项台账**不新增档案盒目录项**，作为盒六动态监控、盒九风险、一车一档随车资料的**盒内子表扩展**（归属见 08 文档 2.2）。以下 6 项台账的**表格范本**（表头格式）由系统预置，与静态制度范本走同一套范本引擎（HTML 表格模板），服务商可在范本管理模块在线修改。

| 专项台账范本 | 表格核心字段 | 归属盒 | 归档形态 |
|-------------|------------|--------|---------|
| 危险货物电子运单 | 运单号、货物品名、危险类别、UN编号、数量、起止地、承运车辆、驾驶员、押运员 | 盒六 动态监控 | 动态台账（法律强制，上传监管平台） |

| 危险品运输台账 | 日期、运单号、品名、吨位、路线、驾驶员、押运员 | 盒六 动态监控 | 动态台账（每日汇总） |
| 押运员在岗记录 | 运单号、押运员、在岗起止、签字 | 盒六 动态监控 | 动态台账（与电子运单匹配） |
| 800公里线路台账 | 线路、风险辨识结论、路书、双押双驾人员安排 | 盒九 风险管控 | 动态台账 |

> 这 6 项台账范本的字段定义与生成逻辑，落在对应业务模块（电子运单→20 动态监控；装卸查验/危险品运输台账/押运员在岗→危货运输执行；800公里→风险辨识；安全卡→随车资料）。范本引擎只负责**表头格式 + 变量填充**，不承载业务数据采集。

### 7.7 创建企业时分配范本组（多选拼装）

企业创建时（首次接入），勾选**车辆类型（多选）+ 承运危险货物类别（危货必填）**：

- 勾选"厢车" → 拼装：通用制度 + 厢式及封闭运输类
- 勾选"厢车 + 泥头车" → 拼装：通用制度 + 厢式及封闭运输类 + 自卸及工程运输类

### 7.8 企业个性化范本

- 企业可在系统级范本基础上，**修改出本企业版本**（改内容、改岗位职责、增删条款）
- 企业个性化范本**不污染系统级范本**（各企业独立）
- 系统级范本更新时，企业可选择"跟随更新"或"保留个性化"

### 7.9 应急预案（用户确认：通用版 + 危货占位）

> 用户要求：制度生成时**一并生成应急预案**。应急预案是独立于制度/规程的**第三类制度文件**。

#### 7.9.1 生成策略

| 维度 | 策略 |
|------|------|
| 适用范围 | **普货全部车型**（冷链车、罐车、厢式、栏板... 一律用通用版） |
| 版本 | **删掉车型独有项，优化成通用版**（首版即通用版） |
| 危货 | **不生成**，归档时占位提示"需专门第三方安全评价公司出具" |
| 生成时机 | 与制度、规程**联动生成**，一次出全套 |

#### 7.9.2 通用版应急预案结构（多篇）

```
第一篇  总则（编制目的/依据/适用范围/响应分级/预案体系）
第二篇  应急组织机构及职责（指挥部/应急办公室/工作组/值守）
第三篇  应急响应（信息报告/预警/响应启动/处置/支援/终止）
第四篇  后期处置 + 应急保障 + 培训与演练 + 预案管理
专项预案（通用 3 个）：
  ① 道路交通事故专项预案
  ② 车辆火灾事故专项预案
  ③ 恶劣天气专项预案
现场处置方案（通用 6 个）：
  ① 车辆碰撞  ② 车辆起火  ③ 车辆涉水/坠水
  ④ 人员伤亡  ⑤ 办公场所火灾  ⑥（车型无关的通用项）
附件（响应启动指令、应急标识、平面图等）
```

> **通用化改造要点**：把冷链车版中"冷藏机组故障、货物温控失效"这类**车型独有**的现场处置方案删除，只保留所有车型通用的处置方案。后续若某车型有强监管要求需独立专项，再以"车型专项"挂载（但首版一律通用）。

#### 7.9.3 危货应急预案占位

危货企业的应急预案**系统不生成**，归档时在对应归档项标注：

> **「客户自备」**——需专门第三方安全评价公司出具（危货应急预案有法定备案要求，不在系统生成范围）。

归档引擎（《08》文档）处理危货企业的应急预案归档项时，生成一张**占位说明页**（含"该资料需第三方安全评价公司出具"的提示 + 客户自备勾选框），而不是生成空白 PDF。

### 7.10 服务商范本管理模块（版本管理 + 在线修改 + 上传）

> 这是服务商账号的核心能力之一（对应原型 `template_manager.html`）。范本管理是「范本起草与推送」「代录台账」的**前置**——先有范本库，才能起草推送、才能代录生成。

#### 7.10.1 定位与角色

| 项 | 说明 |
|----|------|
| 操作角色 | `服务商账号`（见 01 文档 3.2）。企业账号无范本管理入口（企业只能用服务商推送的范本） |
| 能力 | ① 查看内置范本库 ② 上传更多版本范本 ③ 在线直接修改范本 |
| 下游 | 范本库 → 范本起草与推送、代录台账、制度生成 |

#### 7.10.2 内置版本 = 线下台账集合

系统**内置一套「台账集合」版本**（即线下权威台账格式，82 文件 / 12 档案盒）作为基础范本库，覆盖 11 个档案盒的全部归档项范本（责任书、承诺书、告知书、任命书、通知、制度、会议四段式、培训计划/记录、费用台账、监控台账、应急预案、演练、风险清单、隐患排查、一日三检、事故快报、一人一档、一车一档等）。

> 内置版本标记为「内置」不可删除，作为全系统的**兜底范本**。服务商在此基础上扩展，不影响内置版本本身。

#### 7.10.3 版本管理模型

| 版本类型 | 来源 | 说明 |
|---------|------|------|
| **内置版本** | 系统预置（台账集合） | v1.0，不可删除，可「复制为新版本后修改」 |
| **上传版本** | 服务商上传（.html/.docx） | 针对不同客户/地区/业态的定制版本 |
| **在线修改版** | 服务商在线编辑 | 直接改内置或上传版，或复制出独立版本 |

**关键规则**（版本号 / 版本名由用户自定义）：
- **版本号与版本名由用户定义**：修改范本时弹窗输入"版本号（如 `v2.0` / `2026修订版`）"与"版本名"，系统不再自动套 `v2.0`。
- **保存本范本**：直接覆盖当前范本内容（原地更新），不产生冗余副本。
- **另存为新范本**：将修改后的内容存为一份**独立的新范本**（独立 ID + 用户定义的版本号 / 名），原范本不变；同一范本可存在多个自定义版本。
- 可指定**默认版本**（推送 / 代录时优先使用），版本保留历史可回溯。

#### 7.10.4 在线修改能力

| 能力 | 说明 |
|------|------|
| HTML 源码编辑 | 直接编辑范本 HTML（沿用 4.2 拍板：范本存 HTML） |
| 变量占位 | 右侧「可用变量」面板点击插入 `{{变量}}`（对齐字段字典，见 3.3） |
| 条件段落 | 插入 `{% if post == '驾驶员' %}` 等条件段（对齐 4.3 分层决策） |
| 重置 / 保存 | 重置回原版；保存后生成新版本 |

#### 7.10.5 上传范本的自动结构化

服务商上传 Word/HTML 范本后，系统**自动结构化提取变量**：

```
上传 .docx/.html
  → ① 文本结构化（提取固定条款 + 识别变量位置）
  → ② 变量占位 + 条件段落（把"企业名/人名/岗位/日期"替换为 {{变量}}）
  → ③ 转为 HTML 范本（含 CSS 版式 + 变量占位）
  → ④ 存为系统范本（含元数据：名称、档案盒归属、岗位范围、普货/危货）
```

> 自动结构化后，服务商仍可**在线手动微调**（改版式、补变量、调条件段）。

#### 7.10.6 分组、联动、PDF 预览与同源（已落地）

- **文件夹分组**：范本清单按 `type` 以**文件夹形式分组**（如"所有安全生产责任书放一组"），分组头显示图标 + 组名 + 数量 + 组内序号，可折叠，与电子档案柜盒内分组视觉一致。
- **责任书 ↔ 责任制联动编辑**：安全责任书（按岗位）与《安全生产责任制》共享同一份岗位责任数据（`SYS_DOCS.RESP`），修改任一份，另一份**自动对齐**，保证"责任目标 / 职责 / 考核标准"双向一致。
- **A4 PDF 预览**：范本管理、起草推送、自定义签署均支持生成 **A4 仿真 PDF**（宋体正文 + 红章 + 蓝签名 + 平台页脚），可打印 / 下载。
- **与电子档案柜同源**：范本管理与电子档案柜共用 `assets/archive_shared.js` 数据源（11 档案盒元数据 + 盒二 24 项制度全集与 `YT-ZD` 编号），确保两者"一一对应"，任意一处改动同步可见。

### 7.11 范本起草与推送（服务商 → 企业的闭环）

> 这是服务商「针对不同客户起草不同范本并推送」的核心能力（对应原型 `template_push.html`）。承接 7.10 范本管理，形成「管范本 → 起草推送 → 企业执行 → 回填台账」的完整链路。

#### 7.11.1 闭环流程

```
服务商                          企业
  │                               │
  │ ① 从范本库选范本              │
  │ ② 起草定制（改内容/变量）      │
  │ ③ 选择目标企业 → 推送          │
  │ ───────── 推送 ──────────────→ │
  │                               │ ④ 收到任务清单
  │                               │ ⑤ 按清单逐项「拍照 + 签字」
  │                               │ ⑥ 提交完成
  │ ←──────── 回填 ───────────────│
  │ ⑦ 照片签字填入范本 → 生成台账  │
```

#### 7.11.2 关键设计

| 项 | 说明 |
|----|------|
| 起草定制 | 服务商对选中范本在线改内容/变量（复用 7.10.4 在线修改能力），生成**针对特定客户的草稿** |
| 推送 | 可**多选企业**批量推送，也可单企业定向推送 |
| 企业任务清单 | 企业收到的是**极简任务清单**（每项只需「拍照 + 签字」），无需理解安全生产流程 |
| 回填 | 企业提交后，照片、签字**自动填入范本**，生成台账 PDF |
| 留痕 | 推送记录、企业执行记录（拍照/签字时间）全量留痕 |

#### 7.11.3 与代录的区别

| 维度 | 范本起草与推送 | 代录台账 |
|------|--------------|---------|
| 适用客户 | **会用系统**的客户 | **不会用系统**的客户（小微普货） |
| 企业动作 | 企业自己按清单拍照签字 | 服务商代录照片 + 客户签字 |
| 服务商角色 | 起草 + 推送 + 接收回填 | 全程代操作 |

> 两者共同点：都是服务商把「复杂台账」翻译成「简单动作」，降低客户使用门槛。

### 7.12 自定义文件签署（服务商上传模板 + 可配置盖章/签名锚点）

> **定位**：地方性/区域性的管理要求各不相同、模板各异（如「限行区域登记」「剧毒品道路运输通行证」「长时间停车报告」等），系统无法穷举内置。由**服务商上传当地模板**，**自定义名称**，并在模板上**手动放置盖章模块、签名模块**，生成时复用印章引擎（第六章）与签字库（8.1 一键批量签名），归档到对应档案盒。对应原型 `custom_sign.html`。

#### 7.12.1 与「范本管理」的边界

| 维度 | 范本管理（7.10） | 自定义文件签署（7.12） |
|------|----------------|----------------------|
| 对象 | 系统内置台账范本 + 上传标准范本 | **地方性/区域性非标准文件** |
| 核心编辑 | 变量占位 `{{var}}` + 条件段 `{% if %}` | **盖章锚点 + 签名锚点**（可视化放置） |
| 名称 | 沿用范本名 | **自定义名称**（匹配当地叫法） |
| 产出 | 标准台账 PDF | 带盖章+签名的自定义文件，归档到指定档案盒 |

#### 7.12.2 三要素

1. **上传模板** —— 服务商上传当地管理部门下发的原始模板（docx / pdf / 图片）。
2. **自定义名称 + 归属档案盒** —— 名称自由填写（如「限行区域、登记情况」），归属到 11 个档案盒之一（不新增目录子项，作为盒内文件归档）。
3. **手动放置签署模块** —— 在模板预览上拖拽放置两类锚点：
   - **盖章模块**：章类型（企业公章 / 法人章 / 财务专用章 / 安全生产专用章）、是否必盖。
   - **签名模块**：签署岗位（主要负责人 / 安全管理员 / 驾驶员 / 押运员 / 监控员 / 车队长）、签字方式（复用历史签字 / 线上签 / 打印手签）、是否必签。

#### 7.12.3 生成机制（复用既有能力）

- **盖章**：复用第六章印章引擎——企业已上传真实印章图则用真实章，否则按公司名自动生成圆形红章。
- **签名**：复用 `tpl_signature` 签字库——优先「复用历史签字」，缺失才触发线上签或打印手签（同代录的签字匹配三态）。
- **归档**：生成后回写企业「电子档案柜」，企业账号可查看下载。

#### 7.12.4 适用场景（对应 21 文档危货待补项）

| 待补项 | 落地方式 |
|-------|---------|
| 限行区域管控记录 | 服务商上传当地模板 + 配置盖章/签名 → 自定义签署文件 |
| 剧毒化学品道路运输通行证 | 同上 |
| 长时间停车报告记录 | 同上 |
| 其他区域性文件 | 通用能力，按需新增 |

> **原则**：凡属「不同地区要求不同、模板各异」的文件，一律走「自定义文件签署」，**不做系统硬编码穷举**。

### 7.13 范本套（模板集）管理 —— 服务商多套 + 企业当前应用

> 用户逻辑图拍板：**服务商维护多套全局「范本套」，企业从服务商套实例化「当前应用范本」，可定制并另存为「我的范本」；企业改动涉及制度联动时，提示「保存到当前范本」或「另存为新范本」**。本小节把该逻辑固化。

#### 7.13.1 三层对象模型

```
服务商侧（全局，所有企业可调用）
  ├─ 范本套① 普货通用范本   ← 已上线：含真实 24 项普货制度 + 盒一责任书/承诺书/告知书/任命书/通知 + 盒三~盒十一台账范本
  ├─ 范本套② 普货小微范本   ← 占位（通用骨架，内容待补）
  ├─ 范本套③ 普货规上范本   ← 占位
  ├─ 范本套④ 危货通用范本   ← 占位（危货标签）
  ├─ 范本套⑤ 普货狮山范本   ← 占位（区域版）
  └─ 范本套⑥ 普货乐从范本   ← 占位（区域版）
        │  （企业从任一服务商套「创建企业范本」）
        ▼
企业侧（每企业独立，不污染服务商原版）
  ├─ 当前应用范本（is_current=1）  —— 由服务商套按企业实际岗位微调生成
  │     ├─ 可在线修改 / 联动编辑（修改只落本企业副本）
  │     └─ 另存为 → 生成「我的范本」变体（独立命名）
  └─ 我的范本列表（ent_tpl_set，is_current=0 的历史/变体）
        │
        ▼
 生成台账（根据当前应用范本）
```

#### 7.13.2 服务商侧能力（范本套 CRUD）

| 能力 | 说明 |
|------|------|
| 增 | 新建范本套（命名 + 普货/危货 + 区域 + 初始内容：占位骨架 / 复制普货通用全套） |
| 删 | 删除服务商套（企业已实例化的副本不受影响） |
| 查 | 套列表（标签：普货/危货、全局/区域、含占位、文件数），可设默认套 |
| 改 | 套内文件增删（上传 / 移出）、在线修改、联动编辑、PDF 预览 |
| 全局 | 所有企业均可在「选择服务商范本」时调用任意服务商套 |

#### 7.13.3 企业侧能力（当前应用 + 另存为）

| 能力 | 说明 |
|------|------|
| 选择/更换 | 从服务商提供的整套范本创建企业「当前应用范本」（自动按企业实际岗位微调） |
| 定制 | 在线修改 / 联动编辑，修改只落本企业 `ent_tpl_set.files_snapshot`，不污染服务商原版 |
| 另存为 | 从当前范本配置「另存为我的范本」（独立命名，可切换为当前应用） |
| 我的范本 | 企业可维护多份「我的范本」变体，任一可一键设为当前应用 |

#### 7.13.4 制度联动修订提示（核心闭环）

> 企业在系统中任何「涉及制度联动」的改动（组织架构岗位调整：禁用/恢复、更换人员、调整层级/兼并/职责考核、关联制度），都应在进入「企业范本管理」时提示如何落库。

| 触发点（模块） | 动作 | 落库标记 |
|--------------|------|---------|
| 组织架构（org.html） | 禁用/恢复岗位、更换人员、编辑保存（层级/兼并/职责考核）、关联制度 | 写 `tpl_revision_log`（status=0 待处理）+ 前端 `rd_ent_tpl_revision_v1` 标记 |
| 企业范本管理（template_manager.html） | 进入页时检测待修订标记 → 顶部黄色提示条 | 三个按钮：① **保存到当前范本**（status=1，标记 customized）② **另存为新范本**（status=2，另存为我的范本）③ 稍后处理（status=3） |

**时序**：组织架构改动 → 标记待修订 → 企业进入范本管理 → 提示条出现 → 选择保存/另存为 → 标记清除、范本副本更新。未处理前，提示条持续显示（徽标 + 进入时提示，不打扰日常操作）。

#### 7.13.5 数据归属（对齐 schema.sql）

| 表 | 角色 |
|----|------|
| `tpl_set` | 服务商全局范本套（一套 = 一整套制度包） |
| `tpl_template.group_id` | 指向 `tpl_set.id`，文件归属某一套 |
| `ent_tpl_set` | 企业当前应用范本 + 我的范本变体（含 `files_snapshot` 副本） |
| `tpl_revision_log` | 制度联动待修订登记，提示保存/另存为 |

## 八、范本库数据模型（DDL）

```sql
-- 车辆类型字典（普货14种 + 危货16种）
CREATE TABLE veh_type (
  id           BIGINT PRIMARY KEY,
  code         VARCHAR(50),           -- 类型编码，如 GEN_BOX（普货-厢车）
  name         VARCHAR(60),           -- 名称，如"厢车"
  biz_type     VARCHAR(20),           -- GENERAL/DANGER/PASSENGER
  spec_group   VARCHAR(50),           -- 归属普货制度大类编码（G1厢式及封闭/G2栏板及仓栅/G3集装箱及牵引/G4自卸及工程/G5罐体及散装/G6平板及大件/G7专项功能）；危货则为第一层结构编码（D_TANK罐式/D_BOX厢式包装/D_CONT集装箱/D_CYL气瓶）
  status       TINYINT DEFAULT 1,
  deleted      TINYINT DEFAULT 0
);

-- 企业车辆配置（首次接入勾选，多选）
CREATE TABLE tenant_veh_config (
  id           BIGINT PRIMARY KEY,
  tenant_id    BIGINT,
  veh_type_id  BIGINT,                -- 车辆类型
  danger_class VARCHAR(20),           -- 危货专用：危险货物类别（危货第二层，可多值）
  remark       VARCHAR(200),
  created_at   DATETIME,
  deleted      TINYINT DEFAULT 0
);
CREATE INDEX idx_tenant_veh ON tenant_veh_config(tenant_id);

-- 专项规程分组（车型 → 规程的映射）
CREATE TABLE tpl_spec_group (
  id           BIGINT PRIMARY KEY,
  code         VARCHAR(50),           -- 分组编码：普货 G1~G7；危货第一层 D_TANK/D_BOX/D_CONT/D_CYL
  name         VARCHAR(60),           -- 如"厢式及封闭运输类"
  biz_type     VARCHAR(20),
```

### 8.1 一键批量签名（首次配置完成后，全局能力）

> **用户要求**：系统第一次配置完所有信息后，**主要负责人和安全员一键签名所有东西**，然后直接生成档案盒里所有内容。

**核心机制**：把"签一次、后续复用"的被动复用，升级为**主动的一键批量签名**动作。

```
首次配置完成（企业信息 + 组织架构 + 人员 + 车辆类型齐备）
   ↓
主要负责人 + 安全员 各签一次（小程序手写电子签）
   → 签字入库 tpl_signature（is_default=1）
   ↓
点击「一键签名全部范本资料」
   → 引擎扫描所有档案盒内、需要这两个岗位签字的范本类资料
   → 自动套用默认签字到对应签字栏（主要负责人栏 / 安全员栏）
   → 批量标记"已签字"
   ↓
点击「生成全部档案盒内容」
   → 逐盒、逐项渲染 + 盖公司章 + 生成 PDF + 登记 archive_item
```

| 字段 | 说明 |
|------|------|
| 签名主体 | **主要负责人 + 安全员**（两个关键岗位，覆盖绝大多数范本的落款/审批栏） |
| 签名范围 | **所有档案盒内的所有范本类资料**（制度、预案、责任书、承诺书、告知书、任命书、值班制度…），含应急模块 |
| 触发时机 | 首次配置完成后，由企业手动点击触发（不自动，延续"手动触发"决策 5） |
| 签字栏匹配 | 按"签字岗位"匹配：范本里标了"主要负责人"的栏，自动套主要负责人的默认签字；标"安全员"的栏套安全员签字 |
| 责任书双边签字 | 主要负责人/安全员作为"责任管理人（上级）"的栏自动套；作为"责任人（下级）"的栏同样自动套；**驾驶员等一线人员的签字仍需本人各自签**（不在一键范围） |
| 可回溯 | 一键签名后仍可**单份撤销/重签**，超管可改；操作日志不可改 |

> **边界**：一键签名覆盖的是"**主要负责人 + 安全员**"两个岗位应签的栏位。驾驶员、押运员、监控员等一线人员的签字（如个人责任书、岗前培训）仍需本人签署，不在批量范围内——这是法定"本人签字"要求，不能代签。

> **与既有复用机制的关系**：`tpl_signature` 签字库不变，一键签名本质是"批量触发复用"——一次性把所有范本里这两个岗位的签字栏都填上默认签字，而不是等逐份生成时才带出。

## 九、上级关系与签字（从组织架构获取，已确认）

### 9.1 责任书的"上下级"来自组织架构

> 用户反馈第 1 条：责任书有上下级关系，**上级与下级签**，这个层级关系要从**组织架构图**上获取。

责任书的签字双方是"责任管理人（上级）"和"责任人（下级）"，**不能写死**，必须从组织架构的汇报线读取：

```
责任人（下级）＝ 当前生成范本的人员
责任管理人（上级）＝ 组织架构里该人员的直接上级
```

| 岗位（责任人） | 上级（责任管理人）从哪来 |
|--------------|----------------------|
| 主要负责人 | 无上级 → 公司（单边签字，盖公司章） |
| 安全员 / 监控员 / 行政财务 / 其他管理岗 | 组织架构中该岗位的**直接上级**（通常是安全主要负责人） |
| 驾驶员 / 押运员 | 组织架构中该驾驶员的**直接上级**（通常是安全员/车队长） |

> **依赖**：《06-组织架构.md》必须记录"岗位/人员的汇报关系（上级）"，范本引擎据此填充"责任管理人"。

### 9.2 签字栏随上下级关系变化

| 情况 | 签字栏结构 |
|------|-----------|
| 无上级（主要负责人） | 单边：责任主体（公司盖章）+ 责任人签字 |
| 有上级 | 双边：责任管理人（上级签字）+ 责任人（本人签字） |

### 9.3 签字人补全（修正）

> 用户反馈第 2 条：责任书里没有主要负责人的签字。

**修正**：双边签字必须**两栏都签字**——责任管理人（上级，如安全主要负责人）签一栏，责任人（下级）签一栏。原型漏了上级签字，已修正。

## 十、生成流程（已确认：手动触发）

```
① 客户在 PC/小程序填写关键信息（企业信息、人员、岗位）
    → 存 tenant / person 表
② 客户手动点击"生成"（单个或批量，不自动触发）
    → 引擎读取范本 + 字段字典 + 客户数据 + 岗位内容库 + 组织架构上级关系
    → 填充 {{变量}} + 解析 {%条件%} + 取岗位内容 → 渲染 HTML
    → 签字栏按上下级关系确定（上级/下级）
    → 盖公司章（上传章 或 自动生成红章）
③ 生成 PDF（复用《08》的 PDF 引擎）
    → 存 archive_pdf + 登记 archive_item
④ 签字确认（静态资料的法定动作）
    → 线上电子签（签字入库，后续复用）
    → 或线下签字识别上传（补台账用，同样入库复用）
    → 标记"已签字"
⑤ 归档（进入对应档案盒）
```

**签字确认**是静态资料区别于动态资料的关键：静态资料生成后必须有人签字（责任书签字、承诺书签字），才算"生效"。

### 10.1 签字双通道（已确认）

| 通道 | 方式 | 适用场景 | 复用 |
|------|------|---------|------|
| **线上电子签** | 用户在小程序手写/选择电子签 | 日常正常生成，主要方式 | 签字一次后存入签字库，后续自动复用 |
| **线下签字识别上传** | 拍照纸质签字 → OCR/上传图片 | 补台账（方式二）时用 | 上传的签字同样入库复用 |

> 电子签复用是核心体验优化：用户**签一次**，之后所有范本（责任书、承诺书、告知书...）自动带出该签字，避免每份都重签。

## 附：字段字典管理职责（对用户要求的响应）

> 用户要求"做好字段字典管理"。字段字典是范本引擎的**唯一权威数据源**，管理原则：

1. **统一管理**：所有范本引用的变量，必须先登记到 `tpl_field_dict`，范本里才能用，避免各范本自造变量名导致填充失败。
2. **三级分类**：企业级/人员级/上下文字段，明确数据来源模块，保证填充时能取到值。
3. **随范本扩充**：每新增一个范本，先梳理它用到哪些新字段，补进字典，再写范本。
4. **岗位枚举集中**：岗位（post）作为核心变量，其枚举值统一在字段字典/组织架构里维护，范本条件段落引用枚举值。
