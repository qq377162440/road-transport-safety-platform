# 生产部署与运维手册（E1）

> 面向运维/交付人员。对应《上线整体计划》E1「域名/HTTPS、备份策略、日志与监控告警、资源规格确认」。
> 本文档区分两类内容：**已在沙箱内真实演练通过**（标注 ✅）与**必须依赖真实外部资源、由运营方在生产机执行**（标注 ⏳）。

---

## 一、部署形态与前置条件

| 项 | 值 |
|---|---|
| 编排 | 单体模块化 + Docker Compose（独立生产编排 `docker-compose.prod.yml`） |
| 常驻服务 | frontend / backend / mysql / redis / minio（5 个） |
| 对外端口 | **仅 80 / 443**；数据库、缓存、对象存储、后端均不映射宿主机端口 |
| 镜像 | `safetrans/frontend:${IMAGE_TAG}`、`safetrans/backend:${IMAGE_TAG}`（先 build 后打 tag，或由 CI 推送仓库后 pull） |
| 数据卷 | `safetrans-mysql-data` / `safetrans-redis-data` / `safetrans-minio-data`（显式固定卷名） |
| Compose | ≥ v2.24（用到 `deploy.resources` 与 YAML 锚点）；沙箱演练版本 v2.33.0 |

前置：Docker 20.10+、Compose v2、可用内存 ≥ 8GB、磁盘 ≥ 100GB（含备份留存）、80/443 未被占用、防火墙只放行 80/443。

## 二、资源规格确认 ✅

生产编排为每个服务声明了 `deploy.resources` 上限与预留，避免单服务耗尽宿主机资源：

| 服务 | CPU 上限 | 内存上限 | CPU 预留 | 内存预留 | 依据 |
|---|---|---|---|---|---|
| mysql | 2.0 | 2G | 0.5 | 1G | InnoDB buffer pool + 100 张表 + 连接池 |
| backend | 2.0 | 2G | 0.5 | 1G | Spring Boot 3 + PDF 渲染（openhtmltopdf 峰值内存较高） |
| minio | 1.0 | 1G | 0.2 | 256M | 对象存储，PDF/附件读写 |
| redis | 0.5 | 512M | 0.1 | 128M | 验证码 / JWT 白名单 / 限流计数 |
| frontend | 0.5 | 256M | 0.1 | 64M | nginx 静态托管 |
| **合计** | **6.0** | **5.75G** | **1.4** | **2.4G** | — |

**推荐宿主机规格**（按接入企业数分档）：

| 规模 | 规格 | 数据盘 | 说明 |
|---|---|---|---|
| 试运行 / ≤ 20 家 | 4C8G | 100GB SSD | 满足上表上限并留 2G 余量 |
| 正式运营 / 20~100 家 | 8C16G | 300GB SSD | PDF 批量生成与并发学习场景 |
| > 100 家 | 8C32G + 独立 MySQL | 500GB+ | 建议数据库与对象存储外置为托管服务 |

> 沙箱内已通过 `docker compose -f docker-compose.prod.yml config` 校验资源声明生效。生产上线前需在目标机型上跑一次 `stress_test.py` 复核。

## 三、域名与 HTTPS ⏳（流程已就绪，需真实资源）

### 3.1 需要运营方提供的真实资源

| 项 | 说明 | 责任方 |
|---|---|---|
| 域名 | 例如 `safetrans.example.com`，完成 ICP 备案（中国大陆境内服务） | 运营方 |
| DNS A 记录 | 指向生产机公网 IP | 运维 |
| TLS 证书 | CA 签发，含 `fullchain.pem` + `privkey.pem`；或 certbot 自动签发 | 运维 |
| 服务器 | 满足上表规格，防火墙仅放行 80/443 | 运维 |

### 3.2 部署步骤

```bash
cd server/deploy

# 1) 填写全部凭据（生产编排缺失即启动失败，见 docker-compose.prod.yml 的 :? 约束）
cp .env.example .env
vi .env     # MYSQL_* / REDIS_PASSWORD / MINIO_* / JWT_SECRET / DOMAIN / IMAGE_TAG 全部覆盖

# 2) 放置证书（真实证书替换自签文件）
cp /path/to/fullchain.pem certs/fullchain.pem
cp /path/to/privkey.pem   certs/privkey.pem
chmod 600 certs/privkey.pem

# 3) 渲染 nginx 配置（把 __DOMAIN__ 替换为真实域名）
DOMAIN=safetrans.example.com ./render_nginx_conf.sh

# 4) 校验编排（同时确认资源限制、无端口泄漏）
docker compose -f docker-compose.prod.yml config --quiet && echo OK

# 5) 拉起：生产机不构建，只拉取 CI 预构建并打好 tag 的镜像
docker compose -f docker-compose.prod.yml pull        # 从镜像仓库拉取 ${IMAGE_TAG}
docker compose -f docker-compose.prod.yml up -d --no-build

#    本地演练没有镜像仓库时，用已构建的镜像模拟 CI 产物：
#    docker tag deploy-frontend:latest safetrans/frontend:${IMAGE_TAG}
#    docker tag deploy-backend:latest  safetrans/backend:${IMAGE_TAG}
#    docker compose -f docker-compose.prod.yml up -d --no-build
#
#    `build:` 段保留用于本地/预发自行构建，但生产服务器不需要 Node/Maven 工具链，
#    也不应在上线时引入 npm/Maven 网络的不可控依赖（E1 演练实测 corepack 偶发下载失败）。

# 6) 验证
curl -I http://safetrans.example.com/                 # 301 → https
curl -fsS https://safetrans.example.com/health       # {"code":0,"data":{"status":"UP"}}
docker compose -f docker-compose.prod.yml ps         # 5 服务 healthy
```

### 3.3 HTTPS 策略 ✅（配置已落地并演练）

`nginx.prod.conf.tpl` 提供：HTTP 全量 301 到 HTTPS（保留 `/healthz` 探针与 ACME 校验路径）、TLS 1.2/1.3、`http2 on`、HSTS（1 年 + includeSubDomains）、`X-Content-Type-Options` / `X-Frame-Options` / `Referrer-Policy` / `Permissions-Policy`、`client_max_body_size 25m`（对齐后端上传上限）、gzip、带哈希静态资源 30 天强缓存、`index.html` 不缓存保证发版即时生效、API 反代超时 120s。

**沙箱演练**：用 `certs/gen_selfsigned_cert.sh` 生成自签证书（含 SAN `localhost` / `127.0.0.1`），真实拉起生产编排并验证 301 / 443 / `/health` 全链路（见第十二章执行记录）。自签证书**仅用于演练**，生产必须替换。

## 四、凭据与安全基线 ⏳

`application-prod.yml` 中所有占位符**无默认值**，任一缺失应用启动即失败，杜绝带着 `root123` / `minioadmin` / dev JWT secret 上线。

| 约束 | 落地方式 |
|---|---|
| 应用连接 MySQL 不用 root | `MYSQL_USER` 必填，MySQL 镜像初始化时自动建账号并授权业务库 |
| Redis 强制密码 | `redis-server --requirepass`，后端 `REDIS_PASSWORD` 必填 |
| MinIO 密钥 | `MINIO_ROOT_USER/PASSWORD` 必填，禁止 `minioadmin` |
| JWT 密钥 | `JWT_SECRET` ≥ 32 字节随机串（`openssl rand -hex 24`） |
| `.env` 不入库 | `.gitignore` 已忽略；`*.pem` / `*.key` 亦忽略 |
| 端口收敛 | 仅 frontend 映射 80/443 |
| 匿名接口限流 | 按「客户端 IP + 端点」分桶（E4 修正），`RATE_LIMIT_MAX=60` / `RATE_LIMIT_WINDOW=60`；企业共享出口 IP 时按最大集中登录人数调整，独立 IP 可下调，见 `.env.example` |
| 首次登录改密 | 开户初始密码 `888888` / `123456` 为弱口令，见《上线检查清单》要求强制修改 |

> 开发编排 `docker-compose.yml` 仍保留开发默认值，保证「一条命令拉起」的本地可复现性；两套编排独立，生产不继承开发默认值。

## 五、备份策略 ✅（脚本已落地并演练）

| 项 | 策略 |
|---|---|
| 方式 | `backup.sh --cold` 冷备（暂停 frontend/backend 保证一致性），MySQL 逻辑全备 + Redis RDB + MinIO 卷快照 |
| 频率 | 每日 02:30（`crontab.example`） |
| 保留 | 本机 14 天（`BACKUP_RETENTION_DAYS`），过期自动清理 |
| 异地 | `BACKUP_REMOTE_HOOK` 钩子（rclone / aws s3 / rsync），**生产必须配置** |
| 校验 | `gzip -t` + `tar tzf` 完整性校验后才标记成功 |
| 恢复 | `./restore.sh backups/<时间戳> -y`，覆盖式恢复并轮询 `/health` 至 UP |
| RPO / RTO | RPO ≤ 24h（如需分钟级，另启用 MySQL binlog）；RTO ≤ 30min（A1 实测恢复 < 2min） |

```bash
./backup_cron.sh                              # 手动触发一次完整策略
./restore.sh backups/20261106_023000 -y       # 恢复（A1 已实测逐字段一致）
```

> `backups/` 已 gitignore，备份含真实业务数据，禁止入库、禁止留存于系统盘以外的共享可读位置。生产建议挂载独立数据盘并加密。

## 六、日志与监控告警 ✅（脚本已落地并演练）

### 6.1 日志

- 容器日志统一 `json-file` 驱动，`max-size=50m` × `max-file=5`（每服务上限约 250MB），防止日志撑爆磁盘。
- 业务操作日志落 `sys_oper_log`（A2 切面，新增/更新/删除类接口全量留痕）。
- nginx 访问日志 / 错误日志写入容器内 `/var/log/nginx/`，由 json-file 轮转。
- 巡检与定时备份日志：`monitor/cron.log`、`monitor/weekly.log`、`backups/cron.log`。

### 6.2 巡检项（`monitor.sh`，每 5 分钟）

| # | 检查 | 异常判定 |
|---|---|---|
| 1 | 5 服务 running + healthy | 任一非 healthy |
| 2 | HTTP 入口 301 / HTTPS 首页 200 | 非预期状态码 |
| 3 | `/health` 经 nginx 反代返回 `UP` | 未返回 UP（验证全链路而非仅容器端口） |
| 4 | 根分区使用率 | ≥ `DISK_WARN_PERCENT`（默认 85%） |
| 5 | 最近备份新鲜度 | > `BACKUP_MAX_AGE_HOURS`（默认 30h） |
| 6 | 证书剩余天数 + 容器重启次数 | < `CERT_WARN_DAYS`（默认 14 天）/ 重启 > 5 次 |

异常聚合后通过 `alert.sh` 推送，支持企业微信 / 钉钉 / 飞书 / 通用 JSON webhook；未配置 `ALERT_WEBHOOK` 时只写 `monitor/alerts.log`。巡检报告落 `monitor/last_report.txt`，退出码 1 可直接接外部监控。

```bash
./monitor.sh                    # 手动巡检；0=正常 1=异常
cat monitor/last_report.txt     # 查看最近一次报告
```

## 七、发版与回滚

- 发版：CI 构建并推送 `safetrans/{frontend,backend}:${IMAGE_TAG}` 后，生产机执行 `docker compose -f docker-compose.prod.yml pull && docker compose -f docker-compose.prod.yml up -d --no-build`；数据库迁移由 Flyway 在 backend 启动时自动执行。
- 回滚：`./rollback.sh <git-tag> <备份目录>`（E4 交付，会先备份当前状态再切版本 + 恢复数据）；`--dry-run` 可只预览计划与跨 Flyway 版本告警。
- 上线前正式复测：`docker compose --profile test run --rm e2e ./go_live_check.sh`（E4，四条标准 + 三套回归 14 项全绿才返回 0，可重复运行）。
- 发布清单：`./release.sh`（E4，要求工作区干净，输出 `docs/发布清单.md`，含版本/迁移/镜像/凭据校验/SHA-256）。
- **铁律**：任何发版前先 `./backup_cron.sh`；Flyway 只增版本不回退，数据库回滚一律走备份恢复。
